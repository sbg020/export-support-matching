## 2. 신청 자격 판정 엔진 (1차 필터)

### 2.1 판정 흐름

```
[관리자 단계] 공고 수집 → 텍스트화 → 자격 문장 찾기·유형 분류(사이킷런) → 값 추출(사전·정규식)
           → 관리자 검수 → 승인된 조건만 DB에 게시
[사용자 단계] 맞춤 공고를 열 때(또는 기업 프로필을 저장할 때) 승인된 조건을 그 기업 프로필에 대입
           → 조건별 판정 → 3탭 분류(§2.4): 신청 가능 / 확인 필요 / 신청 불가
```

- 필터링은 **기업마다** 실행한다. 공고 수집 시점에 판정 결과를 저장해 두지 않는다.
- **판정은 규칙으로만 한다.** 머신러닝은 문장 찾기, 유형 분류, 공고 분야 분류에만 쓴다.
- 사용자에게는 **게시된 공고만** 보인다.

### 2.2 정답세트 반입

- 완성된 정답세트 엑셀(프로젝트 폴더에 있는 `EC_신청자격_정답세트_150건*.xlsx` 중 가장 최근 파일)을 원본으로 쓴다.
  - 예전에 받은 `EC_신청자격_정답세트_학습용.zip`의 CSV는 검수 전 초안이다. 엑셀과 다르면 **엑셀을 따른다**.
- 관리 명령 `python manage.py import_eligibility_goldset --xlsx <파일 경로>`를 만든다.
  - 시트 `자격조건`, `공고별_자격요약`, `문장라벨`, `조건유형`, `값사전`을 읽는다.
  - 노란색 검수 열에 값이 있으면 검수 값을 우선 쓴다. `삭제`로 표시된 행은 적재하지 않는다. 실제 열 이름은 §1-8 조사 결과에 맞춘다.
  - 같은 내용을 `backend/data/eligibility_goldset/`에 CSV로 다시 내보내 커밋한다 (학습·테스트 재현용).
  - 정답세트 공고 150건의 상태는 `게시(검수 완료)`, 출처는 `정답세트(2026-11)`로 둔다.
  - 여러 번 실행해도 중복이 생기지 않아야 한다.
- 제출 서류 목록은 기존 `EC_정답세트_150건_통합.xlsx`의 `documents` 시트에서 가져와 공고별로 적재한다.
- 조건 테이블 열은 정답세트 `자격조건` 시트와 같게 한다.
  - `cond_id, parent_id, program_id, scope, kind, group, cond_type, cond_types, check_mode, affects_verdict, field, op, value_raw, value_norm, unit, basis, expr(JSONB), expr_text, certainty, evidence, page, source, note`
  - 추가 열: `importance`(§2.4), `review_status`, `reviewer`, `reviewed_at`
- 조건 유형 29종은 코드표로 적재한다.
  - A01–A11: 프로필로 판정
  - B01–B09: 기업이 직접 답함 (자기신고)
  - C01–C09: 서류·담당자 확인

### 2.3 조건별 판정 규칙

정답세트의 `reference_eval.py`와 **동일한 로직**을 Python으로 구현한다. 결과는 조건마다 `충족 / 미충족 / 모름` 중 하나다.

1. `affects_verdict = 'Y'`인 조건만 판정에 쓴다. `N`인 조건은 공고 상세에 '안내'로만 보여 준다.
2. 필수 조건은 같은 `group` 안에서는 OR, 서로 다른 `group` 사이에서는 AND로 묶는다.
3. 제외 조건은 하나라도 해당하면 신청 불가다.
4. 판정식 요소: `atom`, `all`/`any`/`not`(참·거짓·모름의 3값 논리), `flag`, `intent`, `distributor`, `check`, `true`. 각 요소의 의미는 `reference_eval.py`의 설명을 따른다.
5. 기업 유형은 상하위 관계를 인정한다.
   - 소상공인 ⊂ 소기업 ⊂ 중소기업
   - 업력이 7년 미만이면 창업기업으로 본다.
   - 벤처기업 인증이 있으면 벤처기업으로 본다.
6. 지역 비교 규칙:
   - `site_region`(사업장 소재지)을 비교할 때는 본사 소재지도 포함한다.
   - `전남광주`는 `전남`과 `광주`를 모두 뜻한다.
   - 시·군·구까지 적힌 값은 앞부분이 일치하는지로 비교한다.
7. 프로필 값을 판정식 필드로 바꾸는 규칙:
   - **KSIC → 업종 태그:** 대응표 `backend/data/ksic_industry_tags.csv`를 만든다. 정답세트 `값사전` 시트의 업종 태그를 기준으로 한다. 대응표에 없는 업종이면 업종 조건은 `모름`이다.
   - **`model`:** KSIC 대분류가 C(제조업)이면 `제조`로 둔다.
   - **`intent_export`:** 기존 '수출 계획' 항목에서 가져온다.
   - **`issues`:** §3.2 신청 전 확인 답변과 §5.4 체크리스트 답변에서 가져온다.
   - **`debt_ratio`:** §3.1 재무 입력값으로 계산한다. 자본잠식이면 `issues`에 `A11`을 넣는다.
8. 엄격 판정 함수 `strict_verdict()`는 `reference_eval.py`와 같은 3단계 결과를 그대로 낸다. 3탭 분류(§2.4)는 이 결과 위에 얹는 별도 함수로 만든다.

### 2.4 3탭 분류 규칙 (신청 가능 / 확인 필요 / 신청 불가)

사이트에 게시된 **모든 공고**를 기업마다 아래 규칙으로 세 탭 중 하나에 넣는다.

**조건의 중요도 (`importance`)**

| 값 | 뜻 | 기본으로 해당하는 조건 |
|---|---|---|
| `주요` | 신청 자격을 크게 좌우하며, 기업 정보로 유추할 수 없으면 판단을 미뤄야 하는 조건 | A01–A11(프로필 조건), C01 회원·입주·선정, C05 제품·생산지, C09 사업 고유 조건 |
| `체크리스트` | 기업 정보로 유추할 수 있거나 일반적인 기업이면 대부분 충족해, 신청 준비 중에 확인하면 되는 조건 | B01–B09(자기신고), C02 진단·교육·등록, C03 보유 자료, C04 거래·비용 |

- 기본값은 위 표대로 넣고, 관리자가 검수 화면에서 조건별로 바꿀 수 있다.
- A 유형이 `모름`인 이유가 **기업이 해당 항목을 입력하지 않아서**라면 `주요`로 본다.

**분류 순서**

1. 어떤 조건이든 `미충족`(거짓인 필수 그룹, 참인 제외 조건)이 있으면 → **신청 불가**
2. 그렇지 않고 `주요` 조건 중 `모름`이 있으면 → **확인 필요**
3. 그 밖의 경우(모든 `주요` 조건 충족, `체크리스트` 조건만 `모름`) → **신청 가능**
   - 남은 `체크리스트` 조건은 공고 상세의 '신청 전 확인 체크리스트'로 보여 준다 (§5.3).
   - 카드에 `확인할 항목 N개` 배지를 붙인다.

**사용자 체크에 따른 이동**

- 기업이 상세 화면 체크리스트에서 `충족함` / `해당 없음`을 고르면 그 조건을 `충족`으로 다시 판정한다.
- `충족하지 않음` / `해당함`을 고르면 그 조건을 `미충족`으로 다시 판정한다.
- 답은 사용자·공고·조건별로 저장하고, 답한 날짜를 남긴다. 다시 분류한 결과로 탭을 옮긴다.
  - 확인 필요 공고의 `주요` 조건을 모두 `충족`으로 체크하면 **신청 가능 탭으로 이동**한다.
  - 하나라도 `미충족`으로 체크하면 **신청 불가 탭으로 이동**한다.
- 체크를 취소할 수 있다. 취소하면 원래 분류로 돌아간다.
- 사용자 체크로 바뀐 판정에는 `기업 확인` 표시를 붙여, 시스템이 판정한 것과 구분한다.

### 2.5 공고별 확인 (중복 수혜 B06, 참여 횟수 B07)

- 이 두 유형은 기준이 공고마다 다르므로 프로필에서 한 번에 묻지 않는다.
- `체크리스트` 조건으로 취급해 공고 상세 체크리스트에 **원문 근거 문장과 쪽 번호**와 함께 보여 준다.
- 같은 화면에 마이페이지의 지원 이력(사업명·상태·기록일)을 참고 자료로 보여 준다. 지원 이력이 조건에 해당하는지를 시스템이 대신 단정하지 않는다.

### 2.6 엔진 테스트

- **엄격 판정 회귀 테스트:** `profiles.json`의 가상 기업 16곳 × 정답세트 세부사업 전체를 `strict_verdict()`로 판정한다. 같은 데이터로 `reference_eval.py`를 돌린 결과와 **불일치 0건**이어야 한다.
  - 완성본 정답세트로 조건이 바뀌었으므로 예전 `verdicts.csv`가 아니라 `reference_eval.py`를 다시 실행한 결과와 비교한다.
- **3탭 분류 테스트:** 아래 경우를 단위 테스트로 만든다.
  - 미충족 있음 → 신청 불가
  - 주요 모름 → 확인 필요
  - 체크리스트만 모름 → 신청 가능 + 체크리스트 N개
  - 확인 필요에서 주요 조건 모두 충족 체크 → 신청 가능
  - 미충족 체크 → 신청 불가
  - 체크 취소 → 원래 분류

### 2.7 사이킷런 학습과 공고 375건 반영

**1) 학습** (`backend/ml/train_eligibility.py`)

- 완성된 정답세트로 두 가지 분류기를 학습한다.
  - 문장 라벨 분류기: `문장라벨` 시트로 `자격-필수 / 자격-제외 / 가점 / 제출서류 / 기타`를 분류한다. 글자 n-gram(2~4) TF-IDF와 로지스틱 회귀(class_weight=balanced)를 쓴다.
  - 조건 유형 분류기: `자격조건` 시트의 근거 문장 → 29개 조건 유형. 같은 방식을 쓴다.
  - 공고 분야 분류(C01–C15)는 기존 분류 모델이 있으면 그대로 쓰고, 없으면 같은 방식으로 정답세트의 분야 라벨로 학습한다.
- **학습에는 `split = dev`만 쓴다.** `test`(33건)는 평가에만 1번 쓰고, `제외(중복)`는 쓰지 않는다.
- 평가 결과(문장 라벨 F1, 유형 Macro F1, 자격 문장 재현율)를 `docs/ml/eligibility_eval.md`에 적는다.
- 평가가 끝나면 dev와 test를 합쳐 최종 모델을 1번 다시 학습해 `backend/ml/models/eligibility_v1/`에 저장한다. 평가 수치는 dev만으로 학습한 모델의 것을 보고한다.

**2) 추출기** (`backend/ml/extract.py`)

- 공고 텍스트 → 문장 분류기로 자격·서류 문장 선택 → 유형 분류기로 유형 지정 → 사전·정규식으로 값 추출(지역, 기업 유형, 업종, 금액, 연수, 수출액) → 판정식(JSON) 생성.
- 값이나 판정식을 만들 수 없는 조건은 `check("원문 문장")`으로 두고 `importance`는 유형 기본값을 쓴다.
- 조건마다 `source = 자동추출(eligibility_v1)`과 분류기 확률(`confidence`)을 저장한다.
- `제출서류`로 분류된 문장은 공고의 제출 서류 초안으로 저장한다.

**3) 공고 375건 반영** (`python manage.py ingest_notice_folder <폴더>`)

- 대상 폴더는 프로젝트의 `수출 지원사업 공고문` 폴더다. 실제 파일 수를 세어 보고하고, 375건과 다르면 실제 수를 따른다.
- 파일 이름 또는 해시로 정답세트 150건과 겹치는 공고를 찾는다. 겹치는 공고는 정답세트 데이터를 쓰고 다시 추출하지 않는다.
- 나머지 공고는 텍스트화(§7.5) → 추출(위 2)을 **배치로 1번** 실행한다.
- 공고 메타데이터(공고명, 기관, 접수 기간, 원문 URL)는 텍스트의 첫 쪽에서 정규식으로 뽑는다. 찾지 못한 값은 `-`로 두고 지어내지 않는다.
- 상태와 게시:
  - 자동 추출 공고는 `검수 대기`로 저장한다.
  - 관리자가 공고 관리 화면에서 **`자동 추출 공고 일괄 게시`**를 실행할 수 있다.
  - 일괄 게시된 공고는 카드와 상세에 `자동 추출 · 검수 전` 배지를 붙여 정답세트 공고와 구분한다.
  - 관리자가 개별 검수해 승인하면 배지가 사라진다.
  - 텍스트를 추출하지 못한 공고(이미지형, HWP 변환 실패)는 게시하지 않고 `텍스트 추출 불가` 목록에 둔다.
- 결과 요약은 `docs/ml/batch_report.md`에 적는다.
  - 전체 파일 수, 정답세트 중복 수, 신규 추출 수, 추출 실패 수
  - 공고별 조건 수, 평균 confidence
- 적재 명령은 다시 실행해도 중복이 생기지 않아야 한다.

## 3. 기업 프로필 추가 항목

기존 6단계는 바꾸지 않는다. 그 뒤에 **⑦ 재무·신청 전 확인(선택)** 단계를 추가한다.

- 건너뛸 수 있어야 한다.
- 마이페이지 기업 프로필에서도 같은 항목을 조회하고 수정할 수 있게 한다.
- 기존 저장 키는 바꾸지 않는다. 새 항목은 새 필드와 마이그레이션으로 추가한다.

### 3.1 재무 (직접 입력, DART 연동 없음)

| 필드 | 이름 | 단위 |
|---|---|---|
| `fin_base_year` | 재무 기준연도 | 연도 |
| `revenue_krw` | 당기 매출액 (기존 매출액 필드를 그대로 씀) | 원 |
| `revenue_prev_krw` | 전기 매출액 | 원 |
| `operating_income_krw` | 영업이익 (음수 허용) | 원 |
| `net_income_krw` | 당기순이익 (음수 허용) | 원 |
| `total_liabilities_krw` | 부채총계 | 원 |
| `total_equity_krw` | 자본총계 (0 이하 허용 = 자본잠식) | 원 |

- 입력란 안내 문구: `홈택스 '표준재무제표증명'의 금액을 원 단위로 입력하세요.`
- 계산값은 화면에 보여 주기만 하고 따로 저장하지 않는다. 입력값에서 매번 계산한다.
  - 매출액증가율 = (당기 − 전기) / 전기
  - 매출액영업이익률 = 영업이익 / 당기 매출액
  - 매출액순이익률 = 당기순이익 / 당기 매출액
  - 부채비율 = 부채총계 / 자본총계
  - ROE = 당기순이익 / 자본총계
  - 지속가능성장률(SGR) = ROE × 유보율. 유보율은 1로 가정하고, 화면에 "비상장 중소기업은 배당이 거의 없어 유보율을 1로 가정"이라고 표시한다.
- 상태 표시:
  - 6개 금액이 모두 있으면 `재무 입력 완료`
  - 하나라도 없으면 `재무 미입력`. 적합도에서 재무 요소를 뺀다 (§6.4).
  - 전기 매출액이 0이면 매출액증가율은 `-`
  - 자본총계가 0 이하이면 부채비율·ROE·SGR은 `-`이고 `자본잠식` 배지를 붙인다. 재무 원형은 판정하지 않는다.
- DART 불러오기 버튼이나 연동 코드는 만들지 않는다.

### 3.2 신청 전 확인 (공통 결격 사유 6개)

| 코드 | 질문 |
|---|---|
| B01 | 국세·지방세·4대보험 체납이 있습니까? |
| B02 | 휴업·폐업 상태이거나 어음·수표 부도 상태입니까? |
| B03 | 파산·회생절차·법정관리 중입니까? |
| B04 | 금융기관 신용불량·채무불이행 상태입니까? |
| B05 | 정부지원사업 참여제한이나 협약 의무 불이행 상태입니까? |
| B08 | 사회적 물의·법령 위반으로 제재를 받은 상태입니까? |

- 각 질문의 답은 `해당 없음 / 해당 / 모르겠음` 중 하나다. 아직 답하지 않았으면 `-`로 표시한다.
- `해당`이면 그 코드를 `issues`에 넣는다. `모르겠음`이나 미응답이면 그 조건은 `모름`(체크리스트 조건)이 된다.
- 답한 날짜를 저장하고 `기준일 YYYY.MM.DD`로 표시한다.
- 기존 공통 확인 5개는 다음과 같이 옮긴다.
  - 체납, 신용불량, 휴·폐업, 참여제한 → 위 표의 B01·B04·B02·B05로 옮긴다.
  - '자부담 납부 가능' → 결격 사유가 아니므로 기존 '준비 상태' 영역으로 옮긴다. 이 항목도 삭제하지 않는다.
  - 기존 저장값은 원본을 남긴 채 새 필드로 복사한다 (revision_01 §1-3).
- 업종 제외(사행·유흥 등)와 기업 유형 제외(대기업 등)는 묻지 않는다. 프로필 값으로 자동 판정한다.

## 5. 맞춤 공고 화면 (3탭)

### 5.1 탭

- 탭은 `신청 가능 N` / `확인 필요 N` / `신청 불가 N` 세 개다. 게시된 모든 공고가 셋 중 하나에 들어간다.
- 기업 프로필을 입력하지 않았으면 탭 대신 `기업 정보를 입력하면 공고를 신청 자격별로 나눠 보여 드립니다.` 안내와 입력 버튼을 보여 준다.
- 정렬:
  - 신청 가능: 적합도 높은 순 (같으면 마감 빠른 순)
  - 확인 필요: 확인할 주요 조건이 적은 순 → 마감 빠른 순
  - 신청 불가: 마감 빠른 순
- 마감이 지난 공고는 기본으로 숨기고, `마감 공고 포함` 토글로 볼 수 있다.

### 5.2 카드 (공통 + 탭별)

모든 카드에 기본으로 표시하는 항목:
- 공고 제목
- 신청 마감 일정 (없으면 `-`, 예산 소진 시 마감 등 원문 표현이 있으면 그대로)
- 사업 분류 (C01–C15 이름 배지, 여러 개면 모두)

탭별로 더하는 항목:

| 탭 | 추가 표시 |
|---|---|
| 신청 가능 | **적합도 점수**(§6), `확인할 항목 N개` 배지(체크리스트가 있을 때), `자세히` 버튼 |
| 확인 필요 | `확인할 자격 N개` 배지, 대표 확인 조건 1개 한 줄 요약, `자세히` 버튼 |
| 신청 불가 | 불가 사유 1줄(첫 번째 미충족 조건 요약), `자세히` 버튼 |

- `자동 추출 · 검수 전` 공고는 카드에 그 배지를 함께 붙인다 (§2.7).
- 비교에 추가, 관심 저장 등 기존 버튼은 유지한다.

### 5.3 상세 페이지 (`자세히`)

`자세히`를 누르면 공고 상세 페이지로 이동한다. 공통 영역(공고명, 기관, 접수 기간, 지원 내용, 원문 링크)은 기존대로 두고, 탭별로 아래 영역을 보여 준다.

**신청 가능 공고**
1. **적합도 점수와 계산 방법:** 5개 요소의 값·비중·이유 한 줄, 빠진 요소와 사유, 최종 점수 계산식, 가중치 버전, 계산 기준일, `검증 전 시험값`
2. **신청 자격 체크리스트:**
   - 충족된 조건: 판정 근거(우리 회사 정보 값)와 원문 문장·쪽 번호
   - 아직 확인할 조건: 체크박스 형식(`충족함 / 충족하지 않음` 또는 `해당 없음 / 해당함`). 체크하면 §2.4대로 다시 분류한다.
3. **제출 서류 체크리스트:** 공고의 제출 서류를 체크박스로 보여 준다. 체크 상태는 사용자별로 저장하고, 서류함에 같은 유형 문서가 있으면 `서류함에 있음`을 표시한다.

**확인 필요 공고**
1. **확인이 필요한 신청 자격 체크리스트:** 왜 확인이 필요한지 한 줄(예: `기업 정보에 없는 항목입니다`)과 원문 문장·쪽 번호. 체크하면 §2.4대로 다시 분류해 탭을 옮기고, 화면에 `신청 가능 탭으로 이동했습니다` 같은 안내를 띄운다.
2. 이미 충족된 조건 목록 (접어서 표시)
3. 제출 서류 체크리스트 (신청 가능과 같음)

**신청 불가 공고**
1. **신청할 수 없는 근거:** 미충족 조건마다 조건 내용, 우리 회사 정보 값, **원문 문장과 쪽 번호**를 보여 준다. 같은 그룹(OR) 조건은 묶어서 "아래 중 하나도 해당하지 않음"으로 표시한다.
2. 사용자 체크로 불가가 된 경우 `기업 확인으로 판정` 표시와 `체크 취소` 버튼을 둔다.
3. 기업 정보가 틀렸을 수 있으므로 `기업 정보 수정하기` 링크를 둔다.

- `affects_verdict = N`인 안내 조건은 세 경우 모두 맨 아래 '참고 안내'로 보여 준다.

## 6. 적합도 v1

### 6.1 원칙

- **신청 가능 탭 공고에만 점수를 보여 준다.** 확인 필요·신청 불가 공고는 점수를 표시하지 않는다.
- 계산할 수 있는 요소가 2개 미만이면 점수를 내지 않고 `-`로 표시한다.
- 화면에 각 요소의 값, 비중, 이유 한 줄, 계산 기준일, 가중치 버전, `검증 전 시험값`을 보여 준다.
- 재무 요소 옆에는 다음 문구를 보여 준다.
  `재무 원형과 지원 분야의 연결은 실증 근거가 아니라 선행연구에 기반한 가정이므로, 이용 데이터가 쌓이면 보정합니다.`
- 공고가 여러 사업 분류를 가지면 각 매칭표에서 **가장 높은 값**을 쓴다.

### 6.3 재무 원형 × 사업 분류 매칭표

**재무 원형 판정**

- 중소·중견기업 원자료를 재무 변수 4개(매출액증가율, 매출액영업이익률, 부채비율, 매출액순이익률)로 **19개 군집**으로 나누고, 특징이 비슷한 군집을 묶어 **6개 원형**으로 정리했다.
- 판정 방법:
  1. 기업의 재무 비율을 기준표의 평균·표준편차로 표준화한다.
  2. 19개 군집 중심값 중 가장 가까운 군집을 찾는다.
  3. 그 군집에 지정된 원형을 결과로 쓴다.
- 기준표는 팀이 가진 군집 분석 결과를 관리자가 `/admin/settings`에서 CSV로 등록한다.
  - 기준표 내용: 위 4개 변수별 평균·표준편차(KSIC 중분류별로 다르면 중분류 열 포함), 19개 군집 중심값, 군집 → 원형 대응
- 기준표가 등록되지 않았으면 원형은 `기준 미등록`이고 재무 요소를 뺀다. **임의의 기준값을 만들어 넣지 않는다.**
- 원형 설명표 (화면 안내용):

| 원형 | 특징 | 주로 나타나는 단계 | Higgins SGR 해석 | 전략 방향 | 주요 근거 |
|---|---|---|---|---|---|
| 스타형 | 고성장·고수익 | 초보·유망·성장·강소 | 성장을 수익으로 감당하고 있음 | 공격적 시장 확대, 높은 수준의 진입 | Higgins, Melitz, Uppsala |
| 우량형 | 내수·고수익 | 내수 | 수익 여력은 있지만 아직 수출 전 | 첫 수출 준비에 투자 | Melitz, Greenaway, Manova |
| 보수형 | 저부채 | 전 단계 | 빌릴 여력은 있지만 성장에 소극적 | 위험이 낮은 시장 개발, 점진적 확대 | Myers-Majluf, Ansoff, Uppsala |
| 확장형 | 고성장·고부채 | 내수~성장 | 실제 성장률이 SGR보다 높아 부채로 성장 중 | 자금 부담을 줄이면서 성장 유지 | Higgins, Manova, 전기영(2022) |
| 위축형 | 저성장·고부채 | 내수~성장 | 성장·수익 부진에 부채 부담까지 | 기반 정비, 자부담이 낮은 활동부터 | Myers-Majluf, 길재욱 외(2015) |
| 정체형 | 강소·고부채 | 강소 | 규모는 크지만 성장이 정체되고 부채가 있음 | 시장 다변화, 위험 관리 | Higgins, Ansoff |

- '주로 나타나는 단계'는 설명용이다. 원형 판정에는 쓰지 않는다.

**원형 × 사업 분류 매칭표**

값: 핵심 = 1.0 · 보조 = 0.6 · 표에 없는 분류 = 0.3

| 원형 | 핵심 (1.0) | 보조 (0.6) |
|---|---|---|
| 스타형 | C01 전시회·해외영업, C05 해외규격인증, C07 브랜드개발, C06 홍보·광고 | C04 특허·지재권, C10 서류대행·현지등록, C08 디자인 |

### 6.4 요소와 가중치 (초기값, `/admin/settings`에서 수정 가능)

| 요소 | 비중 | 계산 방법 | 값이 없을 때 |
|---|---|---|---|
| 관심 분야 × 사업 분류 일치도 | 25% | 공고 사업 분류와 기업 관심 분야가 하나라도 겹치면 1, 아니면 0 | 관심 분야를 고르지 않았거나 `잘 모르겠어요`이면 제외 |
| 공고 내용 × KSIC 업종 일치도 | 20% | 공고에 업종 언급(지원 대상·우대·제목·본문의 업종 표현)이 있으면 기업 KSIC 업종 태그와 일치 1 / 불일치 0. 업종 언급이 없는 공고는 기업 업종명·제품 설명과 공고 본문의 글자 2-gram TF-IDF 코사인 유사도(0~1) | KSIC·업종명·제품을 모두 입력하지 않았으면 제외 |
| 수출단계 × 사업 분류 일치도 | 25% | §6.2 매칭표 값 | 수출액을 입력하지 않았으면 제외 |
| 재무 원형 × 사업 분류 일치도 | 25% | §6.3 매칭표 값 | `재무 미입력`, `자본잠식`, `기준 미등록`이면 제외 |
| 가점 충족 | 5% | 공고의 가점 항목 중 기업 프로필로 확인되는 항목의 충족 비율 (예: 인증 보유, 수출 실적, 지역 우대) | 가점이 없는 공고이거나 프로필로 확인할 수 있는 가점 항목이 없으면 제외 |

- 최종 점수 = Σ(비중 × 요소값) / (계산된 요소의 비중 합) × 100. 소수점 없이 반올림한다.
- 빠진 요소는 "재무 미입력으로 제외" 같은 형식으로 사유를 표시한다.
- 가중치를 바꿀 때마다 버전을 남긴다. 적합도 결과에는 가중치 버전을 함께 표시한다.
- 기존 v0 함수는 남겨 둔다. 관리자 화면에서 v0과 v1의 상위 5개를 비교할 수 있으면 좋다 (선택).

## 7. 관리자 영역 (`/admin`)

### 7.1 권한

- 관리 명령 `python manage.py ensure_ops_account`를 만든다.
  - 환경변수 `OPS_LOGIN_ID`, `OPS_LOGIN_PASSWORD`를 읽어 관리자 역할 계정을 만든다.
  - 동작 방식은 `ensure_test_account`와 같다. 환경변수가 없으면 경고만 출력하고 정상 종료한다.
  - REVISION_04에서 관리자 계정 방식이 이미 정해져 있으면 그 방식을 따른다.
- 배포 설정:
  - `build.sh`에 위 명령을 추가한다.
  - `.env.example`과 `render.yaml`(`sync: false`)에 변수 이름만 추가한다.
- 권한 제한:
  - `/admin` 화면과 관리자 API는 관리자 계정만 쓸 수 있다. 백엔드에서 역할을 확인해 아니면 403을 돌려준다.
  - 일반 사용자 메뉴에는 관리자 메뉴를 보여 주지 않는다.
- `ADMIN`, `TEST` 계정은 그대로 둔다.

### 7.2 관리자 홈

- 오늘 수집 건수, 검수 대기, 자동 추출·검수 전 게시 공고 수, 마감 임박(7일 이내), 수집 오류를 보여 준다. 실제 값이 없으면 `-`로 표시한다.

### 7.3 기업마당 API 수집

- 인증키는 환경변수 `BIZINFO_API_KEY`에만 둔다. 화면에는 `설정됨 / 미설정`만 표시한다.
- 키가 없으면 '지금 수집' 버튼을 비활성화하고 이유를 보여 준다.
- 관리 명령 `python manage.py collect_bizinfo`와 '지금 수집' 버튼은 같은 코드를 쓴다. 수집 뒤 텍스트화·추출(§2.7-2)을 이어서 실행한다.
- 수출 분야 필터는 키워드 사전(§7.8)을 쓴다.
- 기업마당 공고 ID로 중복을 막는다. 수집 로그(시각, 건수, 오류)를 남긴다.
- 수집 주기는 설정값으로만 저장한다. 예약 실행 환경이 없으면 "예약 실행 미설정"이라고 표시하고, 설정 방법을 `docs/deploy-render.md`에 적는다. 예약이 되는 것처럼 꾸미지 않는다.

### 7.4 KOTRA·KITA 업로드

두 출처는 API가 없으므로 관리자가 직접 모아 업로드한다. 두 화면은 같은 컴포넌트를 쓰고 `source` 값만 다르게 한다.

1. **양식 내려받기** — CSV 열: `source_notice_id(선택), title, organizer, operator, posted_at, apply_start, apply_end, source_url, file_name, memo`
   - 날짜는 `YYYY-MM-DD` 형식이다. 빈칸을 허용하고, 빈 날짜를 오늘 날짜로 채우지 않는다.
2. **파일 올리기** — CSV 1개와 공고문 파일 여러 개(PDF, HWPX)를 함께 올린다. CSV의 `file_name`으로 공고문 파일과 연결한다.
3. **미리보기·오류 확인** — 행별로 필수값 누락, 날짜 형식 오류, 파일 연결 실패, 기존 공고와 중복될 가능성을 보여 준다.
4. **반영** — 공고를 `검수 대기`로 등록하고 텍스트화와 추출을 실행한다.
5. **업로드 이력·되돌리기** — 업로드 단위로 등록된 공고를 한꺼번에 취소할 수 있다. 이미 게시된 공고는 되돌리기 전에 경고를 보여 준다.

### 7.5 텍스트화 (출처 공통)

- PDF는 pdfplumber로 텍스트를 뽑는다. 이때 다음을 정규화한다: 굵은 글씨로 겹친 문자, 비슷하게 생긴 기호, `\x00`, 사용자 정의 영역 문자.
- HWPX는 XML을 직접 파싱한다.
- HWP는 변환 도구가 설치되어 있으면 변환하고, 없으면 `텍스트 추출 불가`로 표시한다. 관리자가 본문을 붙여 넣을 수 있게 한다.
- 이미지형 공고도 `텍스트 추출 불가`로 표시한다.
- 추출한 텍스트(쪽 구분 포함)와 파일 해시는 DB에 저장한다.
  - Render 무료 디스크는 재배포 때 사라진다. 원본 파일은 외부 저장소가 연결되기 전까지 보관하지 않는다.
  - 화면에는 원본 대신 `source_url`을 링크로 보여 준다.

### 7.6 공고 검수

- 대기 목록을 출처, 접수 상태, 검수 상태, `자동 추출 · 검수 전` 여부로 거를 수 있다.
- 검수 화면 왼쪽에는 원문 텍스트와 쪽 번호를 보여 주고, 근거 문장을 강조한다.
- 오른쪽에는 추출된 조건을 보여 준다.
  - 수정 가능 항목: 필수/제외, group, 유형, `importance`(주요/체크리스트), field/op/value, 판정식, 근거 문장, 쪽, `affects_verdict`, certainty
  - 조건 추가와 삭제가 가능해야 한다.
  - confidence가 낮은 조건(기본 0.6 미만)을 위쪽에 표시한다.
- 사업 분류(C01–C15)와 제출 서류 목록을 수정할 수 있다.
- 승인하면 공고와 조건이 사용자 화면에 게시된다. 반려하면 사유를 남긴다.
- 검수자와 검수 시각을 기록한다.
- 근거 문장이 원문 텍스트에 없으면 경고를 보여 준다.

### 7.7 공고 관리

- 전체 목록을 출처와 상태로 거를 수 있다.
- `자동 추출 공고 일괄 게시` 버튼을 둔다 (§2.7-3). 실행 전에 대상 건수를 확인하는 창을 띄운다.
- 중복 병합: 기업마당·KOTRA·KITA·폴더 적재에서 같은 공고가 들어온 경우를 찾는다. 제목·기관·접수기간 유사도로 후보를 보여 주고, 관리자가 확정한다.
- 수정공고는 버전으로 연결한다. 게시를 중지할 수 있다.

### 7.8 기준·설정 (`/admin/settings`)

다음 항목을 수정할 수 있다. 모든 변경은 버전과 변경자를 남긴다.
- 수출단계 기준: 기존 중기부 통합공고 기준을 초기값으로 쓴다.
- 수출 분야 키워드 사전
- 적합도 가중치 (§6.4)
- 수출단계 × 사업 분류 매칭표 (§6.2)
- 재무 원형 기준표 CSV (§6.3)
- 원형 × 사업 분류 매칭표 (§6.3)
- 조건 유형별 기본 `importance` (§2.4)
- 공개 API 키 발급·폐기 (§9)

## 8. 챗봇 (공고 도우미)

### 8.1 동작 조건

- 로그인한 사용자만 쓸 수 있다. 사용자 화면 오른쪽 아래에 버튼을 두고, 열면 대화 패널이 나온다.
- 환경변수:
  - `ANTHROPIC_API_KEY` (백엔드 전용, `VITE_` 접두사 금지)
  - `ASSISTANT_MODEL` (기본값 `claude-sonnet-5-5`)
- 키가 없으면 버튼에 `준비 중`을 표시하고 비활성화한다. 응답이 오는 것처럼 꾸미지 않는다.
- 사용자별 하루 호출 수를 제한한다 (기본 20회, 설정값). 초과하면 안내 문구를 보여 준다.

### 8.2 답변 방식 (사이트에 등록된 데이터만 사용)

- 백엔드 `POST /api/assistant/chat`에서 처리한다.
  1. 질문과 관련된 **게시된 공고**를 최대 5개 찾는다 (제목·본문 TF-IDF).
  2. 그 공고들에 대해 **판정 엔진이 계산한** 이 사용자의 탭 분류(신청 가능/확인 필요/신청 불가), 적합도, 확인할 조건, 근거 문장·쪽 번호, 제출 서류를 모은다.
  3. 1과 2를 Claude API에 함께 보낸다.
- 시스템 지시에 다음을 넣는다.
  - 답변은 전달된 사이트 데이터만 사용한다.
  - 신청 자격과 적합도는 전달된 값을 그대로 쓰고, 다르게 추측하거나 새로 판정하지 않는다.
  - 전달된 데이터에 없는 내용은 "등록된 공고에서 확인할 수 없습니다"라고 답한다.
  - 지원 금액·날짜·선정 가능성을 지어내지 않는다.
- 답변은 정해진 JSON 형식으로 받아 화면에 렌더링한다. 형식이 맞지 않으면 한 번 다시 요청하고, 그래도 실패하면 오류 안내를 보여 준다.
  - `요약`(2~3문장)
  - `관련 공고[]` (공고명, 탭 분류, 적합도, 근거 문장, 쪽, 공고 상세 링크)
  - `확인 필요 항목[]`
  - `다음 할 일`
- Claude API에 보내는 기업 정보는 판정·적합도에 쓰는 항목으로 한정한다. 사업자등록번호, 대표자명, 연락처는 보내지 않는다.
- 대화 내용은 서버에 오래 보관하지 않는다. 호출 수 집계용 기록(사용자, 시각, 토큰 수)만 남긴다.
- 모델명과 프롬프트 버전을 응답 기록에 남긴다.
- 답변 아래에 다음 문구를 표시한다.
  `AI 답변은 등록된 공고와 판정 결과를 바탕으로 하며, 최종 신청 자격은 공고 원문과 주관기관에서 확인하세요.`

## 9. 공개 API 페이지

기능만 갖춰 두면 된다.

- 읽기 전용 엔드포인트:
  - `GET /api/public/v1/notices` — 게시된 공고 목록. 거를 수 있는 값: 사업 분류, 지역, 접수 상태, 출처
  - `GET /api/public/v1/notices/{id}` — 공고 상세. 자격 조건(판정식, 근거 문장, 쪽)과 출처 URL 포함
  - `POST /api/public/v1/eligibility/check` — 프로필 JSON을 받아 공고별 3탭 분류와 확인할 조건을 돌려준다. 받은 프로필은 저장하지 않는다.
- 인증과 제한:
  - 요청 헤더 `X-API-Key`로 인증한다. 키는 관리자가 `/admin/settings`에서 발급하고 폐기한다.
  - DRF throttle로 호출 횟수를 제한한다.
- 문서:
  - drf-spectacular로 `/api/public/docs`(Swagger UI)를 만든다.
  - 사용자 화면에 `/developers` 페이지를 추가한다. 엔드포인트 목록, 문서 링크, 키 발급 문의 안내를 둔다. 메뉴에는 노출하지 않고 하단 링크로 둔다.
- 응답에 사용자 계정, 기업 프로필, 지원 이력은 넣지 않는다. 공고 응답에는 `source`와 `source_url`을 넣는다.
