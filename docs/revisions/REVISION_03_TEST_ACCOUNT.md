## 0. 목적

1. 로그인 테스트 계정 `TEST`를 만들고, 이 계정에 기업 프로필을 하나 등록한다.
2. 프로필 조건은 다음과 같다.
   - 수출단계는 **내수**
   - 업종은 정답 세트 공고와 **가장 많이 겹치는 산업 분야**
   - 그 밖의 값은 정답 세트(30건, 세부사업 35개)에서 추천이 나오도록 정한다.
3. 이 계정은 시연과 별첨 화면 캡처(로드맵, 추천 결과·적합도)에 쓴다.

## 1. 작업 원칙

1. **기존 기능과 계정을 유지한다.**
   - `ADMIN` 계정, `ensure_demo_user`, 인증 API, 화면 구조는 바꾸지 않는다.
   - 다른 사용자의 프로필도 건드리지 않는다.
2. **추천 결과를 만들어 넣지 않는다.**
   - 공고 ID를 하드코딩해 추천 목록에 끼워 넣거나, 판정·적합도 값을 직접 저장하지 않는다.
   - 결과는 반드시 현재 자격 판정 엔진과 적합도 계산이 만든 값이어야 한다.
3. **프로필은 기존 모델과 폼 필드에 맞춘다.**
   - §4의 값을 기존 필드에 대응시킨다.
   - 대응할 필드가 없는 항목은 새 필드를 만들지 않는다. 건너뛰고 보고서에 적는다.
4. **엔진 로직은 바꾸지 않는다.**
   - §6의 기대 결과와 실제 결과가 다르면 먼저 원인을 기록한다.
   - 허용되는 수정은 §6.3의 업종 사전 보완뿐이다.
5. 조사 → 구현 → 검증을 멈추지 않고 진행한다. §7의 기준일 항목만 조건부로 처리한다.

## 2. 사전 확인 (결과는 `docs/revisions/revision_03_inventory.md`에 기록)

1. **기업 프로필 저장 구조**
   - 모델 이름과 사용자 연결 방식(1:1인지, 1:N인지)
   - 6단계 입력 폼의 필드 목록
   - 업종·지역·기업 규모·관심 분야를 코드로 저장하는지, 문자열로 저장하는지
2. **정답 세트 적재 상태**
   - 공고 30건(세부사업 35개)과 자격 규칙·가점·서류가 DB에 들어 있는지
   - 검수 상태가 무엇인지
   - 적재되어 있지 않으면 이번 작업에서 적재하지 않는다. 계정과 프로필만 만들고, §6 검증은 "보류"로 기록한다.
3. **자격 판정 엔진의 비교 방식**
   - `industry`, `company_type`, `hq_region`, `factory_region` 값을 어떻게 비교하는지 확인한다. 문자열 포함, 코드 일치, 사전 매핑 중 무엇인지 적는다.
   - '소상공인'을 '중소기업'의 하위 개념으로 인정하는지 확인한다.
4. **마감 처리 방식**
   - 추천 목록이 마감된 공고를 숨기는지, 마감 배지만 붙이는지 확인한다.
   - 화면에 표시하는 '기준일'이 무엇인지 확인한다.

|---|---|
| 아이디 | `TEST` (대문자. `test`로는 로그인되지 않아야 한다) |

### 3.1 관리 명령 `python manage.py ensure_test_account`

- 환경변수 두 개를 읽는다. 둘 중 하나라도 없으면 아무것도 하지 않고 경고만 출력한 뒤 정상 종료한다. 배포가 실패하지 않게 하기 위해서다.
- 계정이 없으면 만들고, 있으면 비밀번호만 환경변수 값으로 맞춘다. 비밀번호는 출력하지 않는다.
- §4의 기업 프로필은 **TEST 계정에 프로필이 없을 때만** 만든다.
  - 시연 중에 수정한 프로필이 재배포 때 덮어써지지 않게 하기 위해서다.
  - `--reset-profile` 옵션을 주면 §4 값으로 다시 덮어쓴다.
- 여러 번 실행해도 계정과 프로필이 하나씩만 존재해야 한다.
- 프로필 값은 비밀이 아니다. `backend/…/fixtures/test_company_profile.json` 같은 파일이나 명령 안의 상수로 두어도 된다.

### 3.2 배포와 로컬 반영

- `backend/build.sh`의 `python manage.py ensure_demo_user` 다음 줄에 `python manage.py ensure_test_account`를 추가한다.
- `backend/.env.example`에 `TEST_LOGIN_ID=`, `TEST_LOGIN_PASSWORD=`를 변수 이름만 추가한다.
- `render.yaml`의 envVars에 두 키를 `sync: false`로 추가한다. 값은 사용자가 Render 대시보드에서 입력한다.
- 로컬에서는 `backend/.env`에 값을 넣고 `python manage.py ensure_test_account`를 실행한다.

## 5. 업종과 지역을 고른 근거 (정답 세트 분석)

| 정답 세트의 업종 조건 | 공고 | 식료품 제조업으로 충족되는가 |
|---|---|---|
| 제조업 | P011, P034, P046, P070 | 충족 (식료품 제조업은 제조업에 속함) |
| 농·식품 / 식품 제조 / 농식품 제조업체 | P022-02, P105, P122 | 충족 |
| 신선농산물·가공식품 | P015 | 판단 필요 (원문이 애매) |
| 의료기기, 안경, ICT/SW, 창원 주력산업 | P004, P073, P127, P050 | 불충족 |

- 업종 조건이 있는 공고 중 가장 많은 수를 동시에 만족하는 업종이 **식료품 제조업**이다.
- 지역은 본사 화성시와 공장 이천시를 조합했다.
  - 대부분의 지역 조건이 "본사 **또는** 공장 소재"이기 때문에 두 곳을 나누어 두면 더 많은 공고를 충족한다.
  - 이 조합으로 경기 공고 4건(P022-02, P034, P037, P038)과 전국 공고 3건(P001, P005, P006)을 함께 충족한다.

## 6. 기대 결과와 검증

> 아래 결과는 `검수 전 초안` 규칙에 판정 규칙을 그대로 적용해 계산한 참고값이다.
> 판정 규칙: 같은 그룹은 OR, 다른 그룹은 AND, 제외 조건은 하나라도 해당하면 불가, 프로필로 판단할 수 없는 조건은 확인 필요.
> 검수본 규칙이 초안과 다르면 결과도 달라질 수 있다. 그때는 차이를 보고서에 적는다.

  - 두 공고의 미확인 사유가 화면에 그렇게 표시되는지 확인한다.
- 적합도는 관심 분야 일치 여부에 따라 차이가 나야 한다. 일치 7건이 불일치 2건보다 높게 나와야 한다.

### 6.3 결과가 다를 때

1. 실제 결과와 §6.1·§6.2를 공고별로 비교한 표를 inventory 문서에 남긴다.
2. 각 차이의 원인을 다음 중 하나로 분류한다.
   - ① 검수본 규칙이 초안과 다름
   - ② 업종·지역 값 비교 방식
   - ③ 엔진 오류
   - ④ 프로필 필드 대응 누락
3. **②에 한해서만** 업종 사전에 다음 대응 관계를 추가할 수 있다.
   - 대응 관계: `KSIC C10 식료품 제조업` ↔ `제조업`, `식품 제조`, `농·식품`, `농식품 제조업체`
   - 공고 ID를 조건으로 쓰지 않는다.
   - 다른 공고의 판정이 바뀌지 않았는지 전체 결과를 다시 비교한다.
4. ③으로 판단되면 고치지 말고 재현 방법과 함께 보고한다.
