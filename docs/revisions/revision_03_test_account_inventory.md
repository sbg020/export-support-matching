## 0. 문서의 가정과 이 저장소의 실제 구조

개정 문서는 Django 사용자 모델·DB 프로필·`manage.py ensure_test_account`·`backend/build.sh`·`render.yaml`(Render)을 전제로 한다. 이 저장소에는 그런 구성이 없다.

| 문서가 전제한 것 | 이 저장소의 실제 구조 | 이번 반영 방식 |
|---|---|---|
| Django 사용자 테이블, `ensure_demo_user` | 계정 DB 없음. 로그인은 Vercel 서버 함수(`frontend/api/auth/[action].ts` → `frontend/server/auth/`)가 **환경변수**로만 확인한다 (`DEMO_LOGIN_ID`·`DEMO_LOGIN_PASSWORD`, 데모 아이디 `ADMIN`) | `TEST_LOGIN_ID`·`TEST_LOGIN_PASSWORD`를 같은 방식으로 추가했다. 계정은 환경변수 두 개가 다 있을 때만 생기고, 없으면 테스트 계정 로그인만 막힌다(배포는 실패하지 않는다) |
| `is_staff=False`, `is_superuser=False` | 관리자 권한·관리 화면 자체가 없다 | 서버가 역할 `demo`/`test`만 돌려준다. 역할은 화면에서 계정별 프로필 저장 범위를 고르는 데만 쓴다 |
| DB의 기업 프로필(사용자 1:1) | 기업 프로필은 **브라우저 localStorage**(`export-support-matching:profile:v1`) 한 키에만 저장된다. 서버로 보내지 않는다 | 테스트 계정만 전용 키(`…:profile:v1:account:TEST`)를 쓴다. 그 키가 비어 있을 때만 §4 값을 넣는다 → 계정 1개·프로필 1개 (브라우저마다) |
| `--reset-profile` | 관리 명령 없음 | 테스트 계정으로 로그인했을 때 기업 프로필 화면에 `테스트 프로필 초기화` 버튼(확인 창)을 둔다 |
| `backend/build.sh`, `backend/.env.example`, `render.yaml` | 백엔드는 배포하지 않는다(골격만). Render 설정 파일 없음 | 해당 없음. 대신 루트·`frontend/.env.example`에 이름만 추가하고, Vercel 프로젝트 환경변수에 값을 넣었다 |

## 1. 사전 확인 (§2)

### 1.1 기업 프로필 저장 구조

- 모델: `CompanyProfile` (`frontend/src/types/profile.ts`), 상태 `frontend/src/stores/profileStore.ts`. 사용자 연결 없음 — 브라우저 하나에 프로필 하나(기기 공용). 이번에 테스트 계정 전용 범위를 추가해 **테스트 계정 1 : 프로필 1**(브라우저마다)이 되었다. 데모 계정(ADMIN)과 비로그인은 그대로 기기 공용 키를 쓴다.
- 6단계 입력 폼 필드 (`/profile`):
  1. 기본정보: `companyName`, `businessNumber`(세션에만, 저장 안 함), `companyType`, `foundedAt`, `hqRegion`·`hqDistrict`, `hasFactory`·`factoryRegion`·`factoryDistrict`, `employeeCount`
  2. 기업 규모: `companySize`, `industryInputMode`·`ksicCode`·`industryName`, `revenueKrw`·`revenueYear`
  3. 수출 현황: `exportUsdLastYear`, `exportPeriodStart`·`exportPeriodEnd`, `exportCountries[]`
  4. 주력 제품: `productName`, `hsCodeStatus`·`hsCode`
  5. 가점 요소: `certificationStatus`·`certifications[]`·`certificationOther`, `ipStatus`·`ipTypes[]`·`ipOther`
  6. 관심 분야: `interestAreas[]`(13개), `interestUnsure`
- 저장 형태: 지역 = 시·도 **코드**(`gyeonggi`) + 시·군·구 **문자열**, 업종 = KSIC 코드 **문자열**(`C10`) + 업종명 문자열, 기업 규모·형태 = **코드**, 관심 분야 = **코드**(`market-research` 등) → 세부 분야 C01~C15로 매핑(`INTEREST_CATEGORIES`).
- 공통 확인(자기 신고)은 별도 저장(`esm.selfChecks.v1`)이다. 테스트 계정은 이것도 전용 키(`…:account:TEST`)를 쓴다.

### 1.3 자격 판정 엔진의 비교 방식 (`frontend/src/lib/engine/eligibility.ts`)

| 필드 | 비교 방식 |
|---|---|
| `industry` | ① 규칙 값·비고에서 KSIC 코드(예: `C24`, `KSIC 582`)를 뽑아 **코드 범위 일치**. ② 값이 `제조업`이면 KSIC 앞 2자리 10~34. ③ 그 밖의 업종 설명은 자동 판정하지 않고 확인 필요(`not-automatable`). 이번에 ③ 앞에 **업종 설명 사전**을 추가했다(§6) |
| `company_type` | **사전 매핑**: `중소기업`→소상공인·중소기업, `소상공인`→소상공인, `중견기업`, `대기업`, `법인`·`법인사업자`, `개인사업자`. 사전에 없는 유형(예: 농업인, 생산자단체)이 섞이면 확인 필요 |
| `hq_region`·`factory_region` | **사전 매핑 + 문자열 앞부분 일치**: 시·도 이름(`경기`, `경기도` 등)→지역 코드 비교, 시·군·구가 있으면 입력한 시·군·구의 앞부분 비교(`화성시`). 공장 조건에서 공장 없음은 미충족 |
| 공통 | 같은 그룹 필수 조건 OR, 다른 그룹 AND, 제외 조건 해당 시 불가. **규칙의 `certainty`가 `ambiguous`(해석 애매)이거나 예외 문구가 있으면 그 규칙만으로 신청 불가를 만들지 않는다**(확인 필요로 낮춤, REVISION_02 §6.7) |

- 소상공인 → 중소기업: **인정한다.** `중소기업` 토큰이 `small-business`(소상공인)와 `sme`를 모두 포함한다. 테스트 프로필의 기업 규모는 `small-business`(소상공인)로 두어 '중소기업' 조건과 P006 '소상공인' 조건을 함께 충족한다.

### 1.4 마감 처리와 기준일

- 맞춤 추천 목록은 마감 공고를 **숨기지 않는다.** 추천 카드는 마감일(날짜)만 보여 주고 마감 배지는 없다. 전체 공고 카드·상세는 `접수상태 (기준일 …)`와 `D-n (기준일 …)`을 보여 주고, 마감순 정렬은 마감 공고를 맨 뒤로 보낸다.
- 화면의 기준일 = 데이터셋 `meta.asOf`(변환 시 `--as-of`). 접수상태·마감 여유·업력·수출단계 기준 연도가 이 날짜로 계산된다. 시스템 날짜는 쓰지 않는다.
- 변경 전 기준일은 `2026-10-30`(접수중 42 · 마감 16 · 미상 10)이었다.

## 6. 업종 사전 보완 (§6.3)

- **원인 ② 확인.** '농·식품'(P022-R06), '식품 제조'(P122-R05), '농식품 제조업체'(P105-R01, 기업 유형 필드)가 업종 설명으로 분류되어 확인 필요였다. '제조업'은 기존 규칙(KSIC 10~34)으로 이미 충족이었다(P011·P034·P046·P070).
- **추가한 대응:** `식품 제조`·`농·식품`·`농식품 제조업체` → KSIC 10(C10 식료품 제조업). 공백을 뺀 값이 정확히 같을 때만 쓰며, 부분 일치는 쓰지 않는다(예: '수산식품'·'인삼제품류 제조'는 그대로 확인 필요). 공고 ID는 쓰지 않는다.
- **한 방향으로만 쓴다.** 입력 KSIC가 C10이면 '해당'이다. C10이 아니면 지금처럼 확인 필요이며 '불일치'를 만들지 않는다. '농·식품'에는 농업 등 다른 업종도 들어갈 수 있기 때문이다. 기업 유형 필드에서는 사전에 없는 유형 중 사전에 있는 업종 설명이 입력 업종과 맞을 때만 '해당'으로 본다.
- **영향 범위 (전체 68개 행 재비교):** 테스트 프로필 기준으로 조건 3개만 바뀌었다 — P022-R06, P122-R05, P105-R01이 확인 필요에서 충족으로. 공고 상태와 적합도는 68개 모두 그대로다. C10이 아닌 프로필은 이 사전으로 판정이 바뀌지 않는다(테스트 C35).
- 엔진 버전 `eligibility-0.2.0` → `eligibility-0.2.1`(판정 규칙은 같고 사전만 추가). `docs/contracts/engine-cases.json`에 C34·C35를 추가했다.
