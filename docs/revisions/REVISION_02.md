# REVISION_02 — 테스트 데이터 연결 · 수출단계–지원분야 매칭 · 적합도 v0 · 커뮤니티 · Top 10 · 공고 비교 개선

> **사용 방법**
> 이 파일을 프로젝트 루트(`CLAUDE.md`와 같은 위치)에 두고 Claude Code에 다음과 같이 요청한다.
> `CLAUDE.md, docs/revisions/revision_01.md, REVISION_02.md를 모두 읽고 REVISION_02를 로컬과 배포 사이트에 반영해줘.`
>
> **우선순위**
> `CLAUDE.md`와 revision_01의 서비스 원칙(가상 데이터 금지, 결측값 `-`, 자격·적합도 분리, 근거 없는 점수 금지, 기존 저장 키 보존)은 그대로 유지한다. 이 문서와 충돌하는 부분은 이 문서를 따른다. 이 문서에는 비밀값이 없다.
>
> **배포 대상**
> 로컬 개발 환경과 기존 배포 사이트 `https://exportsupportmatching.vercel.app/`를 모두 갱신한다. 이번 요청은 커밋·푸시·배포까지 포함한다.
>
> **이번 개정의 성격**
> 실제 공고 데이터를 처음 연결하는 **테스트 사이트** 단계다. 데이터는 팀이 기업마당에서 모은 수출지원 공고 원문을 정리한 정답 세트 초안(검수 전)이다. 화면은 이것이 테스트 데이터이며 사람 검수 전이라는 사실을 숨기지 않는다.

## 1. 목표와 반드시 지킬 제약

**목표:** 정답 세트 초안 60개 공고를 웹에 연결해, 기업정보 입력 → 수출단계 진단 → 자격 판정 → 적합도 정렬 → 비교·준비까지 실제 데이터로 시연할 수 있게 한다. 커뮤니티(지원사업 후기 · 지원사업 정보방)와 Top 10은 화면 구조와 운영·집계 규칙을 완성한다.

**반드시 지킬 제약**

1. **원문에 없는 값은 만들지 않는다.** 쉬운 설명, 지원 대상 요약, 활용 예, 선정 후 의무, 예상 준비 시간, 원문 URL은 정답 세트에 없으므로 `null`이다. AI로 요약문을 새로 생성해 채우지 않는다.
2. **테스트 데이터임을 숨기지 않는다.** 공고·판정·적합도가 나오는 모든 화면에 데이터 출처, 기준일, '검수 전 초안' 상태를 표시한다 (§3.6).
3. **최종 평가용 test 30건은 쓰지 않는다.** 정답 세트 `inventory_150`의 split이 `test 후보`(그룹 포함)인 공고는 사이트 데이터에 넣지 않고, 규칙·가중치·키워드 조정에도 쓰지 않는다. 변환 스크립트가 이를 검사한다 (§3.2).
4. **근거 없는 수치는 계속 `-`다.** 후기·조회 데이터가 없으면 평균·순위·건수를 만들지 않는다. 브라우저 저장소에 조회 기록을 쌓아 인기 순위처럼 보이게 하지 않는다.
5. **기존 데이터와 기록은 보존한다.** 기존 저장 키(`export-support-matching:profile:v1`, `esm.applicationRecords.v1`, `esm.compareSelection.v1`)의 이름과 형식을 바꾸지 않는다. 새 필드는 없으면 `null`로 읽는다.

## 3. 테스트 데이터셋

### 3.1 입력과 범위

| 항목 | 내용 |
|---|---|
| 입력 | 위 두 xlsx의 `programs`, `rules`, `bonuses`, `documents` 시트. 공고 그룹 정보는 2차 파일의 `inventory_150` 시트를 쓴다 (2차가 최신) |
| 포함 | 두 파일의 모든 공고 행. `review_status`가 `삭제`인 행은 제외 |
| 제외 | split이 `test 후보`인 공고(있으면 변환 실패로 처리), 초안이 없는 나머지 공고 |
| 데이터 기준일 | `2026-10-30` (2차 초안 작성일). 변환 인자 `--as-of`로 받고 JSON에 기록한다 |
| 공고 ID | 정답 세트 ID를 그대로 쓴다 (`P001`, 세부사업은 `P004-01`). 재변환해도 ID가 바뀌지 않는다 |

### 3.2 변환 스크립트

- 위치: `tools/dataset/build_test_dataset.py` (Python 3.12, `openpyxl`). 의존성은 `tools/requirements.txt`에 따로 둔다 (백엔드 requirements에 섞지 않음).
- 실행 예:

  ```bash
  python tools/dataset/build_test_dataset.py \
    --input "수출 지원사업 공고문/정답세트/EC_정답세트_초안_30건.xlsx" \
    --input "수출 지원사업 공고문/정답세트/EC_정답세트_초안_랜덤30건.xlsx" \
    --inventory-from "수출 지원사업 공고문/정답세트/EC_정답세트_초안_랜덤30건.xlsx" \
    --source-urls "수출 지원사업 공고문/정답세트/source_urls.csv" \
    --as-of 2026-10-30 \
    --out frontend/src/data/test-dataset.json \
    --report docs/data/test-dataset-report.md
  ```

- 출력 JSON은 **결정적**이어야 한다. 같은 입력이면 같은 바이트가 나오도록 ID순으로 정렬하고, 빌드 시각 대신 입력 파일의 SHA-256을 `meta`에 기록한다.
- JSON 구조:

  ```json
  {
    "meta": {
      "schemaVersion": 1,
      "datasetVersion": "test-2026-10-30",
      "asOf": "2026-10-30",
      "dataState": "draft",
      "sources": [{ "file": "...xlsx", "sha256": "...", "rows": { "programs": 35, "rules": 268 } }],
      "counts": { "announcements": 60, "programs": 68, "rules": 548, "bonuses": 89, "documents": 512 }
    },
    "programs": [ /* Program 68개 */ ]
  }
  ```

- **변환을 멈추는 오류:** 파일 간 `program_id` 중복, 없는 공고를 가리키는 규칙·서류·가점, 사전에 없는 `field`·`op`, C01~C15 밖의 분류 코드, `test 후보` 공고 포함.
- **경고로 남기고 진행:** 숫자로 읽을 수 없는 금액(값은 `null`, 원문 표현은 메모에 보존), 근거 문장이나 쪽 번호가 빈 규칙, 게시일·접수기간이 없는 공고.
- 보고서(`docs/data/test-dataset-report.md`)에 시트별 행 수, 제외한 행, 경고 목록, §3.4의 파생값 분포(접수상태 등), §6.6의 공통 확인 키별 규칙 수·예외 문구가 있는 규칙·공통 확인으로 다 덮이지 않는 규칙 목록, §8.3의 정산 방식·최대 자기부담 금액 분포를 적는다.

### 3.5 원문 URL

- 정답 세트에는 원문 URL 열이 없다. URL을 추측하거나 기업마당 검색 주소를 만들어 넣지 않는다.
- 검수자가 확인한 URL만 `수출 지원사업 공고문/정답세트/source_urls.csv`(`program_id,source_url,checked_at`)에 적는다. 변환 스크립트는 이 파일이 있으면 읽고, 없으면 모든 `sourceUrl`을 `null`로 둔다. 빈 CSV(머리글만)를 만들어 커밋한다.
- URL이 없으면 기존 원칙대로 `공고 원문 -`이고 `원문 보기`는 비활성이다. 이유 문구: `원문 링크는 검수 과정에서 등록됩니다. 원문 파일: {sourceFile} ({쪽}쪽)`.

### 3.6 데이터 상태와 화면 표시

- `dataState`는 `'draft'`(AI 초안, 사람 검수 전), `'reviewed'`(사람 검수 완료), `'verified'`(검수 완료 + 원문 URL + 검수일) 중 하나다.
- 공고 단위로 계산한다. 그 공고의 programs·rules·documents 행이 모두 `review_status ∈ {확인, 수정, 추가}`이면 `reviewed`, 여기에 원문 URL과 검수일까지 있으면 `verified`, 그 외는 `draft`다. 현재 데이터는 전부 `draft`다.
- 공통 컴포넌트 `DataSourceNotice`를 만들어 전체 공고, 맞춤 추천, 공고 상세, 공고 달력, 수출 로드맵 상단(제목 아래 한 줄)에 둔다.
  - 한 줄: `테스트 데이터 · 기업마당 수출지원 공고 60건(검수 전 초안) · 기준일 2026-10-30`
  - 펼침(`자세히`): `공고 원문에서 정리한 초안이며 사람 검수 전입니다. 자격 판정과 적합도는 이 초안으로 계산한 시험 결과입니다. 실제 신청 전에는 반드시 공고 원문을 확인하세요.`
  - 숫자와 날짜는 JSON `meta`에서 읽는다 (하드코딩 금지).
- 판정 배지(신청 자격·조건별 상태)와 적합도 옆에 `초안 기준` 작은 꼬리표를 붙인다. 색만으로 구분하지 않는다.
- 데이터가 연결되지 않은 경우(`not-connected`)에는 기존 빈 상태 화면을 그대로 쓴다.

### 3.7 저장소 연결

- `StaticProgramRepository`를 추가한다. JSON은 `import('@/data/test-dataset.json')` **동적 import**로 읽어 별도 청크로 분리한다 (첫 화면 번들에 넣지 않음).
- `DataSourceStatus`에 `{ kind: 'test-dataset'; asOf: IsoDate; datasetVersion: string; programCount: number }`를 추가한다.
- 저장소 선택 순서: `VITE_API_BASE_URL`이 있으면 API → `VITE_DATA_SOURCE=test-dataset`이면 테스트 데이터 → 그 외 빈 저장소. 테스트 실행 환경의 기본값은 계속 빈 저장소다 (`app.spec.ts` 유지).
- `list(query)`는 클라이언트에서 검색·필터·정렬한다.
  - 검색 대상: 공고명, 세부사업명, 주관·수행기관, 세부 분야 이름, 금액 메모, 원문 파일명
  - 지역 필터: 선택한 지역의 공고와 함께 전국 공고도 보여 준다. 필터 안내에 `전국 대상 공고도 함께 표시됩니다`를 적는다.
  - `total`은 실제 결과 건수(숫자)다. 데이터가 연결된 상태에서 필터 결과가 0이면 `조건에 맞는 공고가 없습니다`와 필터 초기화 버튼을 보여 준다.
- `useProgramList`의 `sourceConnected`는 `source.kind !== 'not-connected'`로 바꾼다.

## 5. 수출단계 진단 v1

### 5.1 타입 분리

```ts
/** 기업의 수출단계 (직전 연도 수출액 기준) */
export type ExportStage = 'domestic' | 'beginner' | 'promising' | 'growth' | 'strong'

/** 공고의 지원 단계 (기존 SupportStage 유지) */
export type SupportStage = 'preparation' | 'market-entry' | 'execution' | 'localization'
```

`ExportStageDiagnosis.stage`를 `ExportStage`로 바꾼다. 이를 쓰는 기업 진단·로드맵 화면과 테스트를 함께 고친다.

| 수출단계 | 직전 연도 수출액 (USD) |

| 내수 | 1,000 미만 |
| 초보 | 1,000 이상 ~ 100,000 미만 |
| 유망 | 100,000 이상 ~ 1,000,000 미만 |
| 성장 | 1,000,000 이상 ~ 5,000,000 미만 |

### 5.3 진단 규칙

- `exportUsdLastYear`가 `null`이면 진단하지 않는다 (`-`).
- 측정 기간이 직전 연도 1월~12월(데이터 기준일 연도 − 1)이 아니면 단계는 표시한다. 다만 `측정 기간이 직전 연도(1~12월)와 달라 참고용입니다` 안내를 붙인다.

- 기업 진단 화면에는 수출단계, 판단 근거(입력 수출액·측정 기간·기준 구간), 권장 지원 단계(§7.3의 ◎, ○), 다음 단계 조건, 진단 기준일·버전·출처를 표시한다.

| 수출이행 | C13, C14, C15 | 시장진출 (C13: 샘플·소량 발송), 사후관리·현지화 (C15: 원산지 사후검증) |
| 사후관리·현지화 | C03 | 수출이행 (C03: 계약 검토) |

- 공고의 `supportPhases`는 `supportCategories`의 주 단계와 함께 걸치는 단계를 모두 합친 집합이다. 분류가 비어 있으면 `null`이다.
- 매핑 근거: 해외인증은 판매 전에 필요한 조건이라 시장진출에 둔다. 무역보험·통관은 거래·선적 시점의 일이라 수출이행에 둔다. 지사화는 현지 바이어 발굴이 핵심이라 C01·시장진출에 둔다. 국제운송을 수출이행에만 두면 EMS·국제특송 물류비 공고 6건(P024, P077, P098, P100, P110, P141)처럼 소량 수출 기업을 겨냥한 공고가 초보 기업 추천에서 밀리므로 시장진출에도 걸친다.
- 이 표는 가설이다. 화면의 `추천 기준 안내`에 버전과 함께 표시한다.

### 6.6 자격 규칙 v2 (`rules` 시트 → `EligibilityRule`)

기존 `EligibilityRule`(kind 9종)을 아래 형태로 **교체**한다. 정답 세트의 필드 이름을 그대로 써서 원문 근거와 추적이 끊기지 않게 한다.

```ts
export type RuleField =
  | 'company_type' | 'hq_region' | 'factory_region' | 'business_age_years' | 'industry'
  | 'revenue_krw' | 'export_usd' | 'employees' | 'certification' | 'product_hs'
  | 'intent' | 'manual_check'
export type RuleOp = 'in' | 'not_in' | '>=' | '>' | '<=' | '<' | 'between' | 'has' | 'not_has' | 'no-limit' | 'none'
export type CommonCheckKey = 'closure' | 'tax-arrears' | 'credit' | 'sanction' | 'financial-health'

export interface EligibilityRule {
  id: string                         // rule_key (예: P001-R01)
  kind: 'required' | 'exclusion'     // 필수 / 제외
  group: string | null               // 필수 조건 그룹. 같은 그룹은 OR, 다른 그룹은 AND. 제외 조건은 null
  scope: string | null               // 특정 지원 항목에만 붙는 조건이면 그 이름
  field: RuleField
  op: RuleOp                         // '제한없음' → 'no-limit', '-' → 'none'
  value: string[] | number | [number, number] | string | null
  unit: 'USD' | 'KRW' | '명' | '년' | null
  basis: string | null               // 판정 기준 시점 원문 표현 (신청일, 2025년 (직접 수출) …)
  certainty: 'clear' | 'ambiguous'   // 명확 / 애매
  label: string                      // 변환 스크립트가 만든 표시 문구
  commonCheckKey: CommonCheckKey[] | null
  commonCheckUncovered: string[]     // 공통 확인 키워드로 덮이지 않는 항목 (예: '4대보험 미납'). 키가 없거나 모두 덮이면 []
  exceptionText: string | null       // 값의 괄호나 note에 있는 '예외' 문구. 없으면 null
  source: SourceReference            // quote = 근거 문장, locator = 'n쪽', url = 공고 sourceUrl
  note: string | null
  review: { author: string; status: string; source: string }
}
```

- `label` 예: `기업 유형: 중소기업`, `본사 소재지: 경남 진주시`, `수출 실적: 있음`, `직전 연도 수출액: 2,000만 달러 이하`. 제외 조건은 앞에 `제외 — `를 붙인다.
- `commonCheckKey`는 `manual_check` 규칙의 **값(`value`)**에 아래 말이 있으면 붙인다. 여러 개를 붙일 수 있다.
  - 괄호 안은 예외·예시이므로 지우고, 띄어쓰기도 지운 뒤 비교한다 (예: '불량 거래처' → `credit`). '부도덕'은 `부도`로 보지 않는다.
  - 근거 문장(`evidence`)은 보지 않는다. 근거 문장에는 이웃 조건이 함께 들어 있어 키가 잘못 붙는다 (예: P001-R09 '수출바우처 수행기관으로 참여 중'에 `sanction`).

  | 키 | 이름 | 들어 있는 말 | 규칙 · 공고 (정답 세트) |
  |---|---|---|---|
  | `closure` | 휴·폐업 | 휴업, 폐업, 휴·폐업 | 25 · 25 |
  | `tax-arrears` | 국세·지방세 체납 | 체납 | 34 · 32 |
  | `credit` | 금융 연체·신용 | 연체, 신용불량, 채무불이행, 부도, 회생, 파산, 불량거래, 법정관리, 회수의문 | 36 · 25 |
  | `sanction` | 참여제한·제재 | 참여제한, 제재, 부정행위, 부정수급, 부정당 | 21 · 20 |
  | `financial-health` (신규) | 재무 상태 (결산 기준) | 부채비율, 자본잠식, 감사의견 | 6 · 5 |

  키가 붙는 규칙은 모두 96개(35개 공고)이고 전부 제외 조건이다. 수가 다르면 보고서에 이유를 적는다.
- 신용등급 조건(P005-R11 `한국무역보험공사 수출자 신용등급 R급`)에는 키를 붙이지 않는다. 연체·신용 문제가 없어도 특정 기관의 등급은 따로 확인해야 하므로 공고별 직접 확인으로 둔다.
- `commonCheckUncovered`: 키가 붙은 규칙의 값에서 괄호 안 내용과 앞머리 `공통 결격사유:`를 지우고, 숫자 사이가 아닌 쉼표로 나눈다. 나눈 항목 중 어느 키의 말도 없는 항목을 넣는다. 정답 세트 기준 4개 규칙이다: P006-R05 `사업자 미등록`, P022-R11 `금융자산 압류`, P100-R07 `4대보험 미납`, P124-R09 `지원결정 후 자진포기`.
- `exceptionText`: 값의 괄호 안이나 `note`에 '예외'가 있으면 그 문구를 넣는다 (예: P001-R05 `재기지원 인정 기업은 예외`, P067-R11 `신용·기술신용 BBB 이상 또는 업력 3년 미만 중소기업은 예외`). 정답 세트 기준 14개 규칙(9개 공고)이고, 그중 7개는 공통 확인 키가 붙은 규칙이다.

- `manual_check` 중 값·근거에 '중복', '기수혜', '동일 사업', '타 기관'이 있는 규칙은 공고의 `duplicateSupportNotes`에도 근거로 넣는다. 원문 문장만 옮기고, 중복 여부는 판정하지 않는다.

### 6.7 필드별 판정 규칙

조건 결과는 기존과 같이 `met`(충족) · `unmet`(미충족) · `needs-check`(확인 필요)다. `needs-check`에는 이유 코드 `missing-input`(입력 없음) · `not-automatable`(자동 판정 불가) · `period-mismatch`(기준 기간 다름) · `ambiguous`(해석 애매) · `exception`(예외 있음)을 붙인다.

| 필드 | 판정 |
|---|---|
| `company_type` | 값(쉼표로 나눈 토큰) 중 하나라도 맞으면 충족 (OR). 중소기업 ← 소상공인·중소기업, 소상공인 ← 소상공인, 중견기업 ← 중견기업, 대기업 ← 대기업, 법인 ← 법인사업자, 개인사업자 ← 개인사업자. 괄호 안 표현은 메모로 둔다. `companySize`가 없거나 '잘 모르겠어요'면 `missing-input`. 농가·창업기업·상장기업·비영리처럼 프로필로 알 수 없는 토큰만 남으면 `not-automatable` |
| `hq_region`, `factory_region` | 시·도 코드가 같고, 규칙에 시·군·구가 있으면 그것도 같아야 충족. 시·군·구는 공백과 끝의 '특례시·시·군·구'를 떼고 비교한다. 시·도가 다르면 미충족. 시·군·구가 필요한데 프로필에 없으면 `missing-input`. 공장 조건에서 `hasFactory === false`면 미충족. `전국`은 충족 |
| `industry` | 값에 '제조업'이 있고 KSIC 코드가 있으면 앞 2자리 10~34일 때 충족. 값에 5자리 KSIC 코드 목록이 있으면(주로 제외 업종) 프로필 KSIC와 앞자리부터 비교한다. KSIC가 없거나 업종 설명만 있으면 `not-automatable`이고, 이유에 기업의 업종명·제품명을 보여 준다 |
| `export_usd` | `> 0`(수출 실적 있음)은 기간과 상관없이 `exportUsdLastYear > 0`으로 판정한다. 금액 기준(`<=`, `<`, `>=`, `between`)은 규칙 기준 시점이 연도(예: 2025년, 전년도 = 게시 연도 − 1)이고 측정 기간이 그해 1~12월과 같을 때만 판정한다. 다르면 `period-mismatch`이고, 이유에 `입력값 기준으로는 충족/미충족`을 함께 적는다. `unit: KRW`이면 환산하지 않고 `not-automatable`. 공고 문구가 '직수출'이면 이유에 `입력한 수출액이 직수출 기준인지 확인해 주세요`를 붙인다 |
| `revenue_krw` | `revenueKrw`·`revenueYear`로 `export_usd`와 같은 방식으로 판정 |
| `employees` | `employeeCount`와 비교. 없으면 `missing-input` |
| `business_age_years` | 기준 시점이 공고일이거나 비어 있으면 `sourcePublishedAt`, 마감일이면 `applyEnd`를 기준으로 만 연수를 계산한다. 그 밖이거나 기준 날짜가 없으면 `not-automatable`. 오늘 날짜를 쓰지 않는다 |
| `certification` | 인증명을 프로필 인증 코드와 맞춘다 (벤처기업 `venture`, 이노비즈 `innobiz`, 메인비즈 `mainbiz`, 수출유망중소기업 `export-promising`, 여성기업 `women`, 장애인기업 `disabled`, 사회적기업 `social`, 기업부설연구소 `research-institute`). 지역 인증 등 알 수 없는 인증만 남으면 `not-automatable`. `certificationStatus`가 `null`이면 `missing-input` |
| `product_hs` | HS 코드가 '확인됨'이면 앞 4자리로 비교한다. '대략'이면 같은 비교에 `ambiguous`를 붙이고, '모름'이나 미입력이면 `missing-input` |
| `intent` | 값에 '수출 중'이 있고 `exportUsdLastYear > 0`이면 충족. 그 외는 `not-automatable` (직접 확인 대상) |
| `manual_check` | `not-automatable` (직접 확인 대상, §6.9) |
| `op = no-limit` | 충족. 이유: `공고에 '제한 없음'이 명시되어 있습니다.` |

- `certainty: 'ambiguous'`인 규칙은 그 규칙만으로 공고를 '신청 불가'로 만들지 않는다. 결과가 미충족이면 `needs-check`(`ambiguous`)로 낮춘다. 조건 옆에는 `해석 확인 필요` 배지를 단다.
- `exceptionText`가 있는 규칙도 그 규칙만으로 '신청 불가'를 만들지 않는다. 결과가 미충족(제외 대상 해당)이면 `needs-check`(`exception`)로 낮추고, 이유에 `예외가 있습니다: {exceptionText}`를 적어 공고별 직접 확인으로 넘긴다. 조건 옆에는 `예외 있음` 배지를 단다.

### 6.8 공고 단위 상태 결정 (`eligibility-0.2.0`)

1. `scope`가 있는 규칙은 전체 상태 계산에서 빼고 `일부 지원 항목에만 적용되는 조건`으로 따로 보여 준다.
2. **필수 조건:** 그룹별로 하나라도 충족이면 그 그룹은 충족이다. 모두 미충족이면 미충족, 그 외는 확인 필요다.
3. **제외 조건:** 회사가 제외 대상에 해당하면 `unmet`(표시 `제외 대상 해당`), 해당하지 않으면 `met`(표시 `해당 없음`), 알 수 없으면 확인 필요다.
4. 미충족 그룹이나 해당하는 제외 조건이 하나라도 있으면 `신청 불가`다. 그렇지 않고 확인 필요가 있으면 `확인 필요`, 모두 충족이면 `신청 가능`이다.
5. 규칙이 하나도 없으면 결과는 `null`이다 (`자격 조건 초안이 없습니다`).
6. 판정 조건: 기존의 "원문 URL·검증일 필수"를 `dataState`로 바꾼다. `draft`·`reviewed`도 판정하되, 결과에 `dataState`와 `basisDate = verifiedAt ?? 데이터 기준일`을 넣는다. `EligibilityResult.sourceUrl`은 `string | null`로 바꾼다.
7. 결과에 `selfCheckedCount`(직접 확인으로 정해진 조건 수)를 넣는다. 화면에는 `신청 가능 (직접 확인 2개 포함)`처럼 표시한다.

### 6.9 직접 확인 (자가 확인)

정답 세트 규칙의 55%(548개 중 299개)는 체납·결격·중복수혜처럼 기업 프로필로는 판정할 수 없는 조건이다. 이런 조건이 하나라도 있으면 '신청 가능'이 나올 수 없으므로, 사용자가 직접 답하는 기능을 둔다.

- **공통 확인 5가지** (맞춤 추천 상단의 접힌 패널 `공통 확인 사항`, 공고 상세에서 링크):
  `휴·폐업 상태가 아닙니다` / `국세·지방세 체납이 없습니다` / `금융기관 연체·불량거래, 부도·회생·파산·법정관리 등 신용 문제가 없습니다` / `정부지원사업 참여제한·제재 중이 아닙니다` / `최근 결산 기준 자본잠식, 부채비율 1,000% 이상, 감사의견 거절·부적정에 해당하지 않습니다` (신규, §6.10)
  각각 `해당 없음`·`해당 있음`·`모르겠음` 중 하나로 답한다. 재무 상태 항목 아래에는 `최근 결산 재무제표 기준입니다. 외부감사 대상이 아니면 감사의견은 '해당 없음'으로 답하세요. 공고마다 기준이 달라(완전자본잠식만 제외하는 공고 등) '해당 있음'을 고르면 공고마다 다시 확인합니다.`를 적는다.
- **공통 확인 적용 규칙:** `commonCheckKey`가 붙은 규칙에 아래 순서로 적용한다 (위에서부터 먼저 맞는 것).

  | 순서 | 조건 | 결과 |
  |---|---|---|
  | 1 | 그 규칙에 공고별 확인 답이 있다 | 공고별 답을 따른다 (공통 답보다 우선) |
  | 2 | `financial-health`가 아닌 키 중 `해당 있음`이 있고, 규칙에 `exceptionText`가 없다 | `unmet` (`제외 대상 해당`) |
  | 3 | 그 밖에 `해당 있음`이 있다 (재무 상태 키이거나 예외가 있는 규칙) | `needs-check`. 예외면 `exception`과 `예외가 있습니다: {exceptionText}`, 재무 상태면 `not-automatable`과 `공고마다 재무 기준이 달라 다시 확인이 필요합니다` |
  | 4 | 붙은 키가 모두 `해당 없음`이고 `commonCheckUncovered`가 비어 있다 | `met` (`해당 없음 (직접 확인)`) |
  | 5 | 붙은 키가 모두 `해당 없음`이지만 `commonCheckUncovered`가 있다 | `needs-check` (`not-automatable`). 이유: `공통 확인으로 확인하지 못한 항목: {항목}` |
  | 6 | 그 밖 (`모르겠음`이 있거나 답하지 않음) | `needs-check` (`not-automatable`) |

- **공고별 확인:** 공고 상세의 조건 목록에서 `not-automatable`·`period-mismatch`·`ambiguous`·`exception` 조건마다 `충족함`/`충족하지 않음`(제외 조건은 `해당 없음`/`해당함`)을 고를 수 있다. `missing-input`은 직접 확인 대신 `기업정보 입력하기`(해당 단계 `?step=n`) 링크를 보여 준다.
- 저장: 새 키 `esm.selfChecks.v1` (localStorage). `{ version: 1, common: {…}, programs: { [programId]: { [ruleId]: { answer, answeredAt } } } }`. 서버로 보내지 않는다.
- 화면에 `직접 확인한 답은 이 기기에만 저장되며, 판정 결과에 '직접 확인'으로 표시됩니다.`를 적고 `직접 확인 모두 지우기`를 둔다. 프로필 삭제와는 별개다.
- 직접 확인한 조건은 `충족 (직접 확인)`처럼 표시해 자동 판정과 구분한다.

### 6.10 재무 관련 자격 조건

재무 변수는 **공고에 적힌 재무 자격 조건을 판정할 때만** 쓴다. 적합도, 맞춤 추천 정렬, 공고 비교의 우열, 수출 로드맵에는 쓰지 않는다 (§7.2, §8.4.2).

| 공고의 재무 조건 | 규칙 · 공고 (정답 세트) | 처리 |
|---|---|---|
| 매출액 상한 (300억 원 이하, 1,500억 원 이상 제외) | 3 · 3 (P049, P079, P088) | 기존 입력 `revenueKrw`로 자동 판정 (§6.7) |
| 연체·채무불이행·부도·회생·파산·불량거래·법정관리 | 36 · 25 | 공통 확인 `credit` (§6.9) |
| 부채비율 1,000% 이상·자본잠식·감사의견 의견거절/부적정 | 6 · 5 (P067, P073, P092, P100, P127) | 공통 확인 `financial-health` (신규). `해당 있음`이면 공고별 확인 |
| 수출자 신용등급 (무역보험공사 R급) | 1 · 1 (P005-R11) | 공고별 직접 확인 (공통 확인 키 없음) |

- 위 조건이 하나라도 있는 공고는 60개 중 29개다.
- **재무 수치는 입력받지 않는다.** 부채비율·자본총계·신용등급 값을 묻지 않고, 공통 확인의 `해당 없음`·`해당 있음`·`모르겠음`만 받는다. 정답 세트 메모에 '재무 데이터가 있으면 일부 자동 판정 가능'이라고 적힌 규칙은 2개(P067-R11, P092-R12)뿐이라, 민감한 재무 정보를 모을 이유가 약하다. 매출액은 기존 입력을 그대로 쓴다.
- 답은 `esm.selfChecks.v1`에만 저장하고 서버로 보내지 않는다 (§6.9).
- 화면에서 재무 조건은 다른 조건과 같은 방식(조건 문구, 판정, 근거 문장·쪽)으로 보여 준다. '재무 상태가 좋아 유리합니다'처럼 우열을 말하는 문구는 쓰지 않는다.
- 판단 근거: 신용 제약이 수출 진입과 수출 규모를 줄인다는 연구는 있지만(부록 B), 재무 상태로 어느 지원사업이 더 맞는지 고를 근거는 없다. 그래서 공고가 직접 정한 재무 조건만 원문 근거로 판정한다.

## 7. 적합도 v0 (시험용)

### 7.1 정렬 순서 (맞춤 추천)

1. 자격 상태: `신청 가능` → `확인 필요` → `신청 불가`
2. 같은 상태 안에서 적합도 높은 순 (적합도 없음은 뒤)
3. 마감일 빠른 순 (마감일 없음은 뒤) → ID

`신청 불가` 공고는 적합도를 계산하지 않는다.

### 7.2 항목

| 키 | 항목 | 값 (0~1) | 계산할 수 없을 때 |
|---|---|---|---|
| `interest` | 관심분야 일치도 | 공고 세부 분야와 관심 분야(§6.3)가 겹치면 1, 같은 지원 단계만 겹치면 0.5, 아니면 0 | 관심 분야 미입력·'잘 모르겠어요' → 제외 |
| `stage` | 단계 일치도 | 기업 수출단계 × 공고 지원 단계 가중치(§7.3)의 최댓값. 공고의 `targetExportStages`에 기업 단계가 있으면 1, 명시돼 있는데 없으면 0 | 수출단계 미진단 → 제외 |
| `text` | 내용 유사도 (시험용) | 기업 문장과 공고 문장의 글자 2-gram TF-IDF 코사인 유사도를, 판정 대상 공고(신청 불가 제외) 전체 안에서 백분위로 바꾼 값 | 기업 문장이 2글자 미만 → 제외 |

- 재무 변수(매출성장률·영업이익률·부채비율·유동비율 등)와 재무 군집은 쓰지 않는다. 재무 상태가 비슷해도 수출 상황은 다를 수 있기 때문이다. 중간발표의 '전략 일치도'는 이 개정에서 뺀다. 공고에 적힌 재무 조건은 적합도가 아니라 자격 판정에서만 다룬다 (§6.10).
- 기업 문장: 업종명 + 제품명 + 수출 대상 국가 + 고른 관심 분야 이름.
- 공고 문장: 공고명 + 세부사업명 + 세부 분야 이름 + 분류 근거 문장 + 업종 조건 근거 문장.
- 백분위는 화면 필터와 상관없이 전체 판정 대상으로 계산해, 필터를 바꿔도 점수가 변하지 않게 한다.
- `lib/engine/textSimilarity.ts`에 순수 함수로 구현한다. 나중에 문장 임베딩(v1)으로 바꿀 수 있게 `similarity(companyText, programText[])` 인터페이스를 둔다.

### 7.3 기업 수출단계 × 지원 단계 가중치 (`STAGE_PHASE_WEIGHTS`, 버전 `stage-phase-v0`)

◎ = 1.0, ○ = 0.5, · = 0.2. 공고를 숨기지 않도록 0은 쓰지 않는다.

| 기업 수출단계 | 수출준비 | 시장진출 | 수출이행 | 사후관리·현지화 |
|---|---|---|---|---|
| 내수 | ◎ | ○ | · | · |
| 초보 | ○ | ◎ | ○ | · |
| 유망 | · | ◎ | ◎ | · |
| 성장 | · | ○ | ◎ | ○ |
| 강소 | · | ○ | ○ | ◎ |

수출 로드맵과 기업 진단의 `권장 지원 단계`도 이 표에서 ◎(우선)와 ○(함께 보기)를 읽어 표시한다.

### 7.4 가점·감점 보정 (`bonuses` 시트 → `Program.bonusItems`)

| 열 | 필드 |
|---|---|
| `bonus_key`, `item`, `effect`, `certainty`, `evidence`, `page` | `id`, `item`, `effectText`, `certainty`, `source` |
| (파생) | `points`: `effect`에서 읽은 점수. '가점 1점' → +1, '5점 감점' → −5. 범위('−1~−4점'), '우선 지원', '동점자 우선'처럼 점수가 하나로 정해지지 않으면 `null` |
| (파생) | `matchKey`: 프로필로 확인할 수 있는 항목이면 인증·지식재산권 코드(§6.7 인증 표 + 특허 `patent`, 상표 `trademark`, 디자인권 `design`). 그 외는 `null` |

- 보정값 = `clamp(round(10 × 해당 항목 점수 합 ÷ 그 공고의 양수 점수 합), −10, +10)`. 감점 항목도 해당하면 합에 들어간다. 점수가 있는 항목이 없으면 보정하지 않는다.
- 점수나 `matchKey`가 없는 항목은 점수에 넣지 않는다. 대신 `확인 필요 가점`으로 근거와 함께 나열한다 (예: '최근 3년 수혜 이력 없음 +2점'은 EC 밖의 이력이라 판정하지 않음).
- 공고가 인정하지 않는 일반적인 강점은 점수에 넣지 않는다.

### 7.5 계산식과 기준

```
기본 적합도 = 100 × Σ(w_k × s_k) / Σ w_k     (계산 가능한 항목만)
최종 적합도 = clamp(round(기본 적합도 + 가점·감점 보정), 0, 100)
```

- 계산 가능한 항목이 2개 미만이면 결과는 `null`이고 이유는 `반영할 수 있는 항목이 부족합니다`이다. 기존 "한 요소라도 없으면 null" 규칙을 이것으로 바꾼다.
- `FitCriteria`를 다음처럼 바꾼다.
  `{ version, status: 'hypothesis' | 'verified', verifiedAt: IsoDate | null, weights: Record<'interest'|'stage'|'text', number>, bonusCap: number, note }`
- `ACTIVE_FIT_CRITERIA` = `fit-v0` (`status: 'hypothesis'`, 가중치 interest 0.40 · stage 0.30 · text 0.30, bonusCap 10).
  - 근거: 기업이 직접 밝힌 필요가 가장 확실한 신호다. 단계 일치도와 내용 유사도는 같은 비중으로 둔다.
- 비교용 `FIT_CRITERIA_CANDIDATES`에 `fit-v0-equal`(각 1/3)도 등록한다. 화면에는 쓰지 않고 이후 Precision@5 비교에 쓴다.
- `reasons`는 기여도(`w_k × s_k`) 큰 순으로 정렬한다. 추천 카드의 '추천 이유'는 `reasons[0]`이다 (예: `관심 분야 '해외 전시회'와 공고 분야 'C01 전시회/행사/해외영업지원'이 일치합니다.`).

### 7.6 화면 표시

- 추천 카드의 `계산 근거 보기`와 공고 상세 `얼마나 잘 맞나요?`에 항목별 표를 보여 준다. 열은 항목, 반영값, 가중치, 기여 점수, 근거다. 제외된 항목은 `-`와 제외 이유로 표시한다.
- 표 아래에 가점·감점 보정과 `확인 필요 가점`을 나열한다.
- 점수 옆에 `시험용 기준 v0 · 검증 전`을 항상 표시한다. 기준 버전, 단계 매핑 버전(`category-phase-v0`, `stage-phase-v0`), 계산 기준일도 함께 표시한다.
- 맞춤 추천 하단 `추천 기준 안내`의 적합도 설명을 위 내용으로 바꾼다. "산정 기준이 확정되기 전에는 점수를 표시하지 않습니다" 문구는 `시험용 기준으로 계산한 점수이며, 사람 평가(Precision@5)로 검증한 뒤 확정합니다`로 교체한다.

| 지식재산권 증빙 | `ip-evidence` |
| 통장 사본 / 4대보험 관련 증명 / 공장등록증 / 부가가치세 과세표준증명 / 제품 소개 자료 | 위 신규 값 |
| 사업신청서, 참가신청서, 서약서, 개인(신용)정보 동의서 | `null`, `isProgramForm: true` (공고 전용 서식) |
| 견적서, 가점 증빙, 평가항목 증빙서류, 기타 | `null` |

공고 상세 `신청 준비`의 체크리스트는 필수 → 해당 시 → 선택 순서로 보여 주고, 원문 서류명과 근거 쪽을 함께 표시한다. 체크 상태는 기존처럼 관리 기록이 있을 때만 저장한다.

### 8.3 정산 방식과 자기부담 금액

현금 여유가 적은 기업이 스스로 판단할 수 있도록 '돈이 언제, 얼마나 드는지'를 원문 근거로만 보여 준다. 부담이 크다·작다고 판단하지 않는다.

**정산 방식 (`Program.settlement`, 변환 스크립트에서 파생)**

```ts
export interface SettlementInfo {
  type: 'reimbursement' | 'mixed'  // 먼저 집행하고 나중에 받음 / 수행기관 이용과 사후 정산 중 선택
  source: SourceReference          // quote = 찾은 원문 표현, locator = null
}
// Program.settlement: SettlementInfo | null
```

| 규칙 | 내용 |
|---|---|
| 찾는 열 | `support_types`, `self_burden`, `amount_note` (띄어쓰기를 지우고 비교). `notes`는 검수용 메모라 쓰지 않는다 |
| `reimbursement` | 사후 정산, 사후 지급, 사후 지원, 후지급, 後정산, 선집행·先집행, 선지출, 선결제, 완료 후 정산, 증빙 후 지급, 월별 지급 |
| `mixed` | '지정수행기관 이용 또는 사후정산'처럼 두 방식 중 고를 수 있다고 적힌 경우 ('또는 사후 정산', '사후 정산 또는') |
| `null` | 위 표현이 없거나 '공급기업에 사후 지급'만 있는 경우 (지원금이 공급기업으로 가므로 기업이 먼저 내지 않는다). 선지급이라고 추정하지 않는다 |
| 예상 분포 | 68행 중 26행(23개 공고): `reimbursement` 25행, `mixed` 1행(P001). 다르면 보고서에 적는다 |

화면 문구는 `reimbursement` → `먼저 집행 후 지급 (사후 정산)`, `mixed` → `수행기관 이용 또는 사후 정산`, `null` → `-`이다. 값 옆에 원문 표현을 함께 보여 준다.

**최대 자기부담 금액 (`OpportunityCostResult.selfPaymentMaxKrw`, 계산)**

- `totalBudgetMaxKrw`와 `maxAmountKrw`가 모두 숫자이고 `총사업비 한도 − 지원금 한도 > 0`일 때만 그 차액을 `최대 자기부담`으로 보여 준다. 근거 문구는 `총사업비 한도 {a} − 지원금 한도 {b}`이고, 타입은 `ValueWithBasis<number> | null`이다.
- 차액이 0이면 계산하지 않는다(`null`). 이런 공고의 자부담은 '한도 초과분', '체재비'처럼 다른 비용이라 0원으로 보이면 안 된다 (P010, P011, P025).
- 정답 세트 기준으로 계산되는 행은 4개다: P001 4,500,000원, P006 1,125,000원, P009 12,000,000원, P028-01 500,000원.
- 비율(`ratioPercent`)과 원문 표현(`selfPayment.note`)은 금액과 함께 계속 보여 준다. 부가세 포함 여부는 원문 표현으로만 알린다.

### 8.4 공고 비교 개선 (revision_01 §9 보완)

비교 영역의 위치(전체 공고 하단 `#compare`), 최대 4개, 저장 키 `esm.compareSelection.v1`과 그 형식은 바꾸지 않는다.

#### 8.4.1 선택 흐름

- 맞춤 추천 카드, 공고 상세, 마이페이지의 `비교에 추가`는 **선택만 바꾸고 화면을 이동하지 않는다.** 이미 고른 공고는 버튼이 `비교에서 빼기`로 바뀐다 (`aria-pressed`). 추가하면 `비교에 추가했습니다 (n/4)` 알림을 띄우고, 5번째는 기존처럼 `최대 4개까지 비교할 수 있습니다.`를 안내한다.
- 공통 컴포넌트 `CompareDock`(하단 고정 바)을 만들어 맞춤 추천, 공고 상세, 마이페이지 관심·준비 중·신청완료 화면에 둔다. 선택이 1개 이상일 때만 보인다.
  - 문구는 `비교 n/4 · 비교하기`다. 누르면 `compareLocation()`으로 이동하고, 도착하면 2개 이상일 때 자동으로 펼치는 기존 동작을 따른다.
  - 1개만 골랐으면 `비교하기`를 비활성으로 두고 `1개 더 고르면 비교할 수 있습니다.`를 보여 준다.
  - 전체 공고의 기존 고정 바(`비교 n/4 · 비교 영역으로 이동`)도 이 컴포넌트로 바꾸되, 이 화면에서는 이동하지 않고 비교 영역으로 스크롤한다.
  - 360px 모바일에서 바가 마지막 카드의 버튼을 가리지 않도록 목록 아래에 바 높이만큼 여백을 둔다.
- 마이페이지 관심·준비 중·신청완료 탭의 목록 행마다 `비교에 추가` 체크박스를 둔다 (전체 공고 카드와 같은 동작). 데이터셋에서 찾을 수 없는 공고의 기록은 체크박스를 비활성으로 두고 `공고 정보를 찾을 수 없어 비교할 수 없습니다.`를 보여 준다.

#### 8.4.2 비교 행

기존 행은 지우지 않는다. `지원규모·방식` 행은 `지원방식`으로 이름을 바꿔 지원방식(원문 표현 병기)만 보여 주고, 금액은 새 `지원금·총사업비 한도` 행으로 옮긴다. 아래 6개 행을 추가하고 자기부담금 행의 표시를 넓힌다. 값이 없으면 `-`이고, 근거와 기준일을 함께 보여 준다.

| 묶음 | 행 (`CompareRowKey`) | 값 | 근거 |
|---|---|---|---|
| 판정 | 확인할 조건 (`checksLeft`, 신규) | `확인 필요 n개 · 직접 확인 m개 반영`. 확인 필요가 없으면 `없음`, 자격 결과가 없으면 `-` | 직접 확인 답을 반영한 `EligibilityResult` |
| 판정 | 해당 가점·감점 (`bonuses`, 신규) | 프로필로 해당이 확인된 `bonusItems`를 `항목 (효과 원문)`으로 나열하고 `확인 필요 가점 n개`를 덧붙인다. 해당 항목이 없으면 `해당 없음`, 가점 항목 자체가 없으면 `-` | §7.4 |
| 기본 정보 | 마감까지 (`deadline`, 신규) | `D-n (기준일 2026-10-30)`. 지났으면 `마감`, 마감일이 없으면 `-`와 `applyPeriodNote` | §8.1 마감 여유 |
| 기본 정보 | 지원금·총사업비 한도 (`amounts`, 신규) | `지원금 {maxAmountKrw} · 총사업비 {totalBudgetMaxKrw}`. 숫자가 없으면 `amountNote` 원문 | 금액 근거 쪽 |
| 준비 부담·기회비용 | 자기부담금 (`selfPayment`, 확장) | 비율, 최대 자기부담 금액(§8.3), 원문 표현 | §8.3 |
| 준비 부담·기회비용 | 정산 방식 (`settlement`, 신규) | §8.3 화면 문구와 원문 표현 | §8.3 |
| 준비 부담·기회비용 | 참여 후기 (`reviews`, 신규) | 후기 5건 이상이면 `실제 자부담 비율 중앙값 · 정산 난이도 중앙값 (후기 n건)`. 그 전에는 `-`와 `후기 5건 이상일 때 표시` (값은 §10.8 서버가 생긴 뒤 채워진다) | §10.6 |

- 어떤 공고가 더 좋다고 판단하지 않는다. 행마다 가장 좋은 값을 강조하거나, 값으로 열 순서를 바꾸거나, `추천`·`유리` 같은 표시를 하지 않는다. 재무 상태로 공고를 고르거나 순위를 매기지 않는다.
- 비교 영역은 `evaluateOpportunityCost`에 §8.1처럼 데이터 기준일을 `today`로 넘기고, 자격 판정에 `esm.selfChecks.v1`의 직접 확인 답을 반영한다.
- 비교 영역 아래 `준비 부담·기회비용을 볼 때` 안내에 `정산 방식이 '먼저 집행 후 지급'이면 지원금을 받기 전에 비용을 먼저 내야 합니다.` 한 줄을 추가한다.

#### 8.4.3 테스트

- 맞춤 추천·공고 상세·마이페이지에서 `비교에 추가`를 눌러도 경로가 바뀌지 않고, 선택 수와 하단 바 문구만 바뀐다.
- 1개를 골랐을 때 `비교하기`가 이유와 함께 비활성이고, 2개 이상이면 비교 영역으로 이동해 펼쳐진다.
- 마이페이지 기록에서 고른 공고가 비교 표에 나오고, 찾을 수 없는 공고는 고를 수 없다.
- 새 행 6개와 자기부담금 확장 표시를 테스트 전용 공고로 확인한다 (차액이 0이면 금액 없음, 정산 방식이 없으면 `-`).
- 기존 저장 키에 저장된 선택이 그대로 읽힌다.

## 9. 새로 올라온 공고 · 많이 본 공고

### 9.1 위치와 구성

- 전체 공고(`/programs`) 화면에서 검색창 위에 `둘러보기` 영역을 둔다. 탭 2개는 `새로 올라온 공고`와 `많이 본 공고`다 (기존 `TabNav` 재사용).
- 홈에는 넣지 않는다 (revision_01 §5 유지).
- 각 탭은 최대 10줄의 간단한 목록이다. 줄마다 순위, 공고명(상세 링크), 주관기관, 접수상태(기준일), 마감일을 보여 준다. 프로필이 있으면 신청 자격 배지도 함께 보여 준다.
- 순수 함수는 `lib/programHighlights.ts`에 둔다: `selectNewPrograms(programs, asOf)`, `rankMostViewed(events, programs, now)`.

### 9.2 새로 올라온 공고

| 규칙 | 값 |
|---|---|
| 기준일 | 게시일(`sourcePublishedAt`). 수집일·검수일은 쓰지 않는다 |
| 기간 | 데이터 기준일 이전 **30일** (`NEW_PROGRAM_WINDOW_DAYS = 30`) |
| 대상 | 접수중·접수예정. 마감·기간 미확인 제외 |
| 묶기 | 같은 원공고(`parentId`)·같은 그룹(`groupKey`)은 1줄로 묶고, 가장 최근 게시 공고를 대표로 둔다. 추가모집·재공고는 `추가모집` 배지 |
| 정렬 | 게시일 최신순 → 마감 빠른 순 → ID |
| 개수 | 최대 10. 모자라도 기간 밖 공고로 채우지 않는다 |
| 안내 | `게시일 기준 최근 30일 · 기준일 2026-10-30`. 게시일이 없어 제외한 공고 수도 표시한다 (예: `게시일 미확인 18건 제외`) |

30일로 둔 이유: 공고일이 확인된 공고를 주별로 세면 0~12건으로 편차가 크다. 테스트 데이터는 10월 말 시점에 접수 중인 공고를 모은 것이라 14일 창에는 거의 남지 않는다 (68행 중 게시일이 있는 50행 기준으로 30일 안은 14행).

### 9.3 많이 본 공고

**집계 규칙 (순수 함수로 지금 구현)**

- 이벤트: 공고 상세를 열 때 `{ programId, occurredAt, visitorKey }`. `visitorKey`는 서버가 만든 익명 키다.
- 같은 방문자의 같은 공고는 하루 1회만 센다. 봇 User-Agent와 `?internal=1` 접속은 제외한다.
- 기간은 실제 현재 시각 기준 최근 7일 이동 창이다 ('이번 주' 월요일 초기화는 쓰지 않음). 조회는 실제 사건이므로 데이터 기준일이 아니라 현재 시각을 쓴다.
- 순위: 순 방문자 수 → 관심 저장 수(가능하면) → 게시일 최신순. 마감 공고는 제외한다.
- 표시 최소 기준: 순 방문자 10명(`MIN_UNIQUE_VISITORS`) 이상인 공고가 3개 이상일 때만 목록을 보여 준다. 그 전에는 `조회 데이터가 충분히 모이면 표시합니다.`
- 이 순위는 추천 점수에 섞지 않는다.

**지금 배포 단계의 처리 (P1)**

- 서버 저장소가 없으므로 이벤트를 저장하지 않는다. `ViewEventSink` 인터페이스와 아무것도 하지 않는 구현만 둔다.
- 탭에는 `조회 집계는 서버 저장소가 연결되면 시작합니다.`를 표시한다. 브라우저 저장소에 기기별 조회를 쌓아 순위처럼 보여 주지 않는다.
- `rankMostViewed`는 테스트 전용 이벤트로 단위 테스트한다 (중복 제거, 7일 창, 최소 기준, 마감 제외).

**서버 저장 (P2)**

- Django 모델 `ProgramViewEvent(program, visitor_key, viewed_on, created_at)`를 만들고, `(program, visitor_key, viewed_on)`에 유일 제약을 둔다.
- `visitor_key`는 세션 쿠키 값을 날짜별 비밀 솔트로 HMAC한 값이다. IP·User-Agent 원문은 저장하지 않는다.
- 이벤트 수집 API와 개인정보 처리 안내 문구는 서버를 배포할 때 함께 추가한다.

- 하위 메뉴는 기존 `SectionNav`로 보여 준다. 글 보기·글쓰기 화면에서는 해당 게시판 탭을 선택 상태로 표시한다 (`activeFor`).
- `/community/reviews/write`, `/community/info/write`가 `:postId`로 해석되지 않게 라우트 순서를 정한다. `:board`는 `reviews`·`info`만 허용하고, 그 외는 404다.
- `app.spec.ts`의 "마이페이지만 로그인이 필요하다" 테스트를 "마이페이지와 커뮤니티 글쓰기만 로그인이 필요하다"로 고친다.

### 10.2 게시판 공통 화면

1. 제목, 한 줄 설명, `SectionNav`(지원사업 후기 | 지원사업 정보방)
2. 도구 줄: 검색(범위 `제목` / `제목+내용`), 정렬(`최신순` / `조회순` / `추천순` / `댓글순`), 말머리 필터, 오른쪽 끝 `글쓰기` 버튼
3. `주간 인기글` 5개(최근 7일 추천순). 글이 5개 미만이면 이 영역을 숨긴다
4. 공지(운영자 글)를 맨 위에 고정하고, 그 아래 글 목록을 둔다 (데스크톱은 표, 모바일은 카드)

   | 열 | 내용 |
   |---|---|
   | 번호 | 게시판 안 순번 (공지는 `공지`) |
   | 분류 | 말머리 (§10.3·§10.4) |
   | 제목 | 제목과 댓글 수 `[3]`. 연결된 공고가 있으면 공고명 칩 |
   | 작성자 | 표시 규칙(§10.5) |
   | 등록일 | 오늘 글은 `HH:mm`, 이전 글은 `YYYY.MM.DD` |
   | 조회 · 추천 | 숫자 |

5. 페이지 번호 (20개씩)
6. 글 보기: 본문, 연결 공고 칩(상세 링크), 추천, 신고, 댓글(답글 1단계까지), 이전·다음 글
7. 글쓰기: 게시판별 양식(§10.3·§10.4), 등록 전 미리보기, 이용 규칙 동의 체크

빈 상태 문구는 `아직 등록된 글이 없습니다.`다. 예시 글이나 가짜 글을 렌더링하지 않는다. 컴포넌트 테스트에는 테스트 폴더 안의 테스트 전용 데이터만 쓴다.

### 10.3 지원사업 후기 (참여 확인 기업만 작성)

- **작성 자격:** 로그인하고 해당 사업 참여가 확인된 기업. 마이페이지 관리 기록이 `selected`·`in_progress`·`completed`이고, 선정 통보·협약서 같은 증빙을 운영자가 확인한 경우다. 확인되면 글에 `참여 확인` 배지를 붙인다.
- **필수 연결:** 공고(ID), 사업 연도·차수, 수행기관(있는 사업만). 같은 기업은 같은 사업·연도·차수에 후기를 1개만 쓰고, 수정할 수 있다.
- **말머리:** `선정 후기` · `수행 후기` · `정산 후기`
- **문항:**

  | 문항 | 형식 |
  |---|---|
  | 지원 내용이 공고와 같았나요? | 같음 / 일부 다름 / 많이 다름 |
  | 신청서류 준비에 걸린 시간 | 시간 (숫자) |
  | 실제 자부담 비율 | % (숫자) 또는 모름 |
  | 정산 난이도 | 1~5 |
  | 수행기관 대응 | 1~5 (수행기관이 있는 사업만) |
  | 성과 | 바이어 연결 / 계약 / 인증 획득 / 해당 없음 (복수 선택) |
  | 다시 참여할 의향 | 예 / 아니요 / 모름 |
  | 제목 · 본문 | 제목 40자, 본문 1,000자 이내. 회사명·개인정보·비방 금지 안내 |

- **표시:** 회사명 대신 `업종 · 수출단계 · 지역`만 보여 준다 (예: `화장품 제조 · 초보 · 경기`).
- **게시:** 운영자 검토 후 게시한다. 검토 중인 글은 작성자에게만 `검토 중`으로 보인다.
- 후기는 자격 판정과 적합도에 섞지 않는다.

### 10.4 지원사업 정보방 (자유 게시판)

- **작성 자격:** 로그인한 회원 누구나
- **말머리:** `질문` · `정보 공유` · `모집·행사 소식` · `자유`
- **공고 연결 (선택):** 글쓰기에서 공고를 검색해 칩으로 붙일 수 있다. 붙인 공고의 상세 화면에는 `정보방 관련 글 n개` 링크가 생긴다.
- **표시:** 회원 닉네임만 보인다. 실명·회사명은 보이지 않고, 운영자 글에는 `운영자` 표시를 단다.
- **금지:** 광고·영업 홍보(수행기관·컨설팅 업체의 유료 서비스 홍보 포함), 개인정보·사업자등록번호·연락처 게시, 비방. 글쓰기 화면에 규칙을 요약해 보여 준다.

### 10.5 권한과 표시 규칙

| 사용자 | 읽기 | 정보방 글·댓글 | 후기 작성 | 추천·신고 |
|---|---|---|---|---|
| 비로그인 | 가능 | 로그인 화면으로 이동 (`redirect` 유지) | 로그인 화면으로 이동 | 로그인 화면으로 이동 |
| 로그인 회원 | 가능 | 가능 | 참여 확인 후 가능 (확인 방법 안내) | 가능 (자기 글 추천 불가) |
| 참여 확인 기업 | 가능 | 가능 | 가능 | 가능 |
| 운영자 | 가능 | 가능, 공지 작성 | 검토·게시·숨김 | 신고 처리 |

- 데모 계정(`ADMIN`)은 일반 회원과 같다 (revision_01 §6.4). 운영자 권한을 주지 않는다.
- 신고가 3건 이상 쌓인 글은 자동으로 가리고 운영자 검토를 기다린다. 권리침해 신고는 임시조치 절차(정보통신망법 제44조의2)를 따른다. 실제 운영 전에 법률 검토를 받는다.
- 글·댓글을 쓸 때 사업자등록번호(숫자 10자리), 전화번호, 이메일 형식이 보이면 등록 전에 경고한다.

### 10.6 공고 상세·기회비용과의 연결

- 공고 상세의 `참여 후기` 섹션(`section-reviews`, `기회비용` 다음)은 **지원사업 후기 게시판에서 그 공고에 연결된 글**을 보여 준다. 별도 데이터나 폼을 만들지 않고 게시판 목록 컴포넌트를 재사용한다.
  - 요약 칸: 후기 수, 실제 준비 시간 중앙값, 실제 자부담 비율 중앙값, 재참여 의향 비율. 후기가 5건 미만이면 `-`와 `후기 5건 이상일 때 표시`
  - 최근 후기 3개와 `지원사업 후기에서 모두 보기` 링크 (`/community/reviews?program=<id>`)
  - `후기 문항 보기` 펼침 영역에 §10.3 문항을 읽기 전용으로 보여 준다
- 후기가 5건 이상이면 기회비용의 `예상 준비 시간`과 `실제 자부담`에 중앙값을 표시하고, 근거로 `참여 후기 n건 중앙값 (기간)`을 적는다.
- 공고 비교의 `참여 후기` 행(§8.4.2)도 같은 기준(5건 이상)으로 실제 자부담 비율과 정산 난이도 중앙값을 보여 준다.
- 정보방에 그 공고와 연결된 글이 있으면 상세 하단에 `정보방 관련 글 n개` 링크를 둔다.

### 10.7 이번 배포 단계의 처리 (P1)

- 게시글을 저장할 서버와 회원 DB가 없으므로, `CommunityRepository` 인터페이스와 빈 구현(`EmptyCommunityRepository`: 빈 목록, 건수 `null`)만 연결한다.
- 화면은 모두 만든다. 목록은 빈 상태이고, `글쓰기`는 비활성이며 이유를 표시한다: `게시글을 저장할 서버와 회원 정보가 아직 연결되지 않아 글쓰기는 준비 중입니다.` 지원사업 후기에는 `참여가 확인된 기업만 쓸 수 있습니다.`를 함께 적는다.
- 글쓰기 화면(`/community/:board/write`)은 로그인 후 열 수 있다. 양식은 보이지만 `등록` 버튼은 같은 이유로 비활성이며, 입력값을 브라우저 저장소에 저장하지 않는다.
- 브라우저 저장소에 글·댓글·추천을 저장해 커뮤니티가 동작하는 것처럼 보이게 하지 않는다. 그런 글은 다른 사람에게 보이지 않는다.

### 10.8 서버 (P2, 회원 DB와 함께)

- 타입: `types/community.ts`에 `CommunityBoard`(`'reviews' | 'info'`), `CommunityPost`, `CommunityComment`, `ReviewAnswers`, `PostAuthorDisplay`, `CommunityQuery`를 둔다 (P1에서 먼저 만든다).
- Django 모델 초안
  - `Post(board, category, title, body, author, program, program_year, program_round, operator_name, review_answers JSON, status[pending/published/hidden], view_count, created_at, updated_at)`
  - `Comment(post, parent, author, body, status)`
  - `Reaction(post, user)`: 추천, 유일 제약
  - `Report(target_type, target_id, reporter, reason, status)`
  - `ParticipationVerification(user, program, year, round, evidence_file, verified_by, verified_at)`
- API: `GET/POST /api/community/{board}/posts`, `GET/PATCH/DELETE /api/community/posts/{id}`, 댓글·추천·신고 엔드포인트. 운영자 검토는 Django admin으로 시작한다.
- 조회수는 §9.3의 순 방문자 규칙(같은 방문자 하루 1회)을 따른다.
- 서버를 배포할 때 이용 규칙과 개인정보 처리 안내를 함께 게시한다.

Vitest와 Django 테스트가 같은 파일을 읽어 같은 결과를 내는지 확인한다.
- 커뮤니티 모델·API는 §10.8을 따르고, 회원가입(revision_01 §6.3에서 `준비 중`)과 같은 회원 DB를 쓴다.
- 백엔드는 이번에도 배포하지 않는다. DB 없이 실행할 수 있는 테스트만 돌린다.

## 13. 로컬·배포 반영 절차

### 13.1 데이터 빌드

1. `tools/requirements.txt`를 설치하고 §3.2 명령으로 `frontend/src/data/test-dataset.json`과 보고서를 만든다.

### 13.3 Git과 배포 제외

- `수출 지원사업 공고문/`의 PDF·PNG 원문은 Git에 올리지 않는다. `.gitignore`에 `수출 지원사업 공고문/**/*.pdf`, `수출 지원사업 공고문/**/*.png`를 추가한다.
  - 이미 추적 중이면 이력을 지우지 말고 `git rm --cached`로 추적만 멈춘 뒤 보고한다.
- 정답 세트 xlsx, `source_urls.csv`, 생성 JSON, 보고서는 커밋한다.
- 루트 `.vercelignore`에 `수출 지원사업 공고문`과 `tools`를 추가한다.
- 이 문서는 비밀값이 없으므로 `docs/revisions/REVISION_02.md`로 옮겨 커밋한다. `CLAUDE.md` 상단의 개정 반영 안내에 revision_02 한 줄을 추가한다.
- `README.md`의 "현재 상태"와 `docs/architecture.md`(데이터 모델, 판정 엔진, 데이터 접근 경계)를 이번 내용으로 갱신한다.
- 커밋은 의미 단위로 나눈다. 예: 데이터 변환, 저장소, 입력 추가, 수출단계, 자격 판정 v2, 적합도 v0, 기회비용, 둘러보기, 커뮤니티, 문서.

### 13.4 배포

- Git 연동 배포: 푸시 → Preview URL에서 §14 확인 → Production 반영. CLI 연동이면 `vercel` → 확인 → `vercel --prod`.
- 접근 권한이 없어 배포하지 못하면 URL을 지어내지 말고, 필요한 연결·설정과 남은 명령을 보고한다.
