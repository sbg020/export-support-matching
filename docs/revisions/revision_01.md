## 1. 목표와 반드시 지킬 제약

**목표:** 중복된 메뉴와 설명을 줄이고, 사용자가 필요한 기능을 쉽게 찾도록 구조를 정리한다.

**반드시 지킬 제약 세 가지**

1. **기업정보 입력 페이지는 그대로 둔다.** 입력 항목, 단계, 디자인, 검증, 임시 저장·저장 로직, 저장 키를 바꾸지 않는다. 공통 레이아웃·내비게이션 연결만 조정한다 (§7).
2. **기능은 삭제하지 않는다.** 중복 기능은 하나로 합치거나 다른 위치로 옮길 수 있지만, 기존에 되던 동작은 새 위치에서 계속 되어야 한다. 화면 하나를 없앨 때는 그 화면의 모든 기능이 어디로 갔는지 §2의 목록에 적는다.
3. **기존 데이터와 기록은 보존한다.** 브라우저 저장소(localStorage 등)의 기존 키를 지우거나 이름만 바꾸지 않는다. 구조를 합칠 때는 원본을 남긴 채 복사·병합한다 (§11.2).

## 2. 코드 수정 전 현황 조사

## 3. 새 정보 구조와 경로

이동하지 않는 화면은 **기존 URL을 그대로 유지**한다. URL은 꼭 필요한 곳만 바꾼다.

### 3.1 경로표

| 영역 | 하위 메뉴 | 경로 | 로그인 |
|---|---|---|---|
| 홈 | - | `/` | 불필요 |
| 로그인·회원가입 | 로그인 / 회원가입 탭 | `/login` (`?mode=signup`이면 회원가입 탭) | - |
| **지원사업 찾기** | 기업정보 입력·저장 | `/diagnose/input` (유지) | 불필요 |
| | 기업 진단 | `/diagnose/result` (유지) | 불필요 |
| | 맞춤 추천 | `/programs/recommended` (유지) | 불필요 |
| **전체 지원사업** | 전체 공고 (하단에 공고 비교 영역) | `/programs` (비교 영역은 `#compare`) | 불필요 |
| | 공고 달력 | `/programs/calendar` (신규, 기존 `/mypage/calendar` 이전) | 불필요 |
| | (하위 메뉴 아님) 공고 상세 | `/programs/:id` (유지) | 불필요 |
| **나의 로드맵** | 수출 로드맵 | `/roadmap` (유지) | 불필요 |
| **마이페이지** (헤더 프로필로 진입) | 기업 프로필 | `/mypage/profile` (유지) | 필요 |
| | 관심·준비 중·신청완료 사업 | `/mypage/programs?tab=interested\|preparing\|applied` (신규) | 필요 |
| | 서류함 | `/mypage/documents` (유지) | 필요 |

### 3.2 기존 주소 리다이렉트

이동·통합된 화면의 기존 주소는 모두 새 위치로 연결한다. 기존 쿼리와 해시는 유지한다.

| 기존 주소 | 새 주소 |
|---|---|
| `/programs/compare` | `/programs?compare=…#compare` (기존 쿼리의 선택 공고 유지) |
| `/mypage/calendar` | `/programs/calendar` (월 등 기존 쿼리 유지) |
| `/mypage` | `/mypage/profile` |
| `/mypage/saved` | `/mypage/programs?tab=interested` |
| `/mypage/preparation` | `/mypage/programs?tab=preparing` |
| `/mypage/history` | `/mypage/programs?tab=applied` |
| §2 조사에서 발견된 그 밖의 이동 화면 주소 | 해당 새 위치 |

### 3.3 라우팅 규칙

- 각 라우트에 `meta.section`(`find` / `programs` / `roadmap` / `mypage` / 없음)과 `meta.requiresAuth`를 둔다. 사이드바와 화면 내 하위 메뉴의 선택 상태는 이 값으로 결정한다.
- 리다이렉트는 Vue Router의 `redirect` 함수로 구현해 `query`와 `hash`를 넘긴다.
- `/programs/calendar`, `/programs/compare`, `/programs/recommended`가 `/programs/:id`의 ID로 해석되지 않는지 확인한다.
- 앱 내부 링크는 경로 문자열 대신 이름 있는 라우트(named route)를 쓴다. 작업 후 소스 전체에서 기존 경로 문자열(`/programs/compare`, `/mypage/calendar`, `/mypage/saved`, `/mypage/preparation`, `/mypage/history`)을 검색했을 때 리다이렉트 정의 외에는 남아 있지 않아야 한다.
- 공고 상세는 `전체 지원사업` 섹션에 속한다. 진입 위치에 따라 `?from=recommended` / `?from=calendar`를 붙이고, 상세의 "목록으로" 링크를 해당 화면으로 연결한다. `from`이 없으면 전체 공고로 연결한다.
- 라우터 `scrollBehavior`에서 해시(`#compare`)로 이동할 때 고정 헤더 높이만큼 여백을 둔다.

## 4. 공통 레이아웃과 내비게이션

### 4.1 왼쪽 상단 공통 사이드바

- 로고(클릭 시 `/`)와 **주 메뉴 3개만** 둔다: `지원사업 찾기`, `전체 지원사업`, `나의 로드맵`.
- 각 주 메뉴는 첫 번째 하위 메뉴로 이동한다.
  - 지원사업 찾기 → `/diagnose/input`
  - 전체 지원사업 → `/programs`
  - 나의 로드맵 → `/roadmap`
- 사이드바에서 하위 메뉴, `공고 비교`, `마이페이지`, `일정` 항목을 제거한다.
- 현재 섹션의 주 메뉴는 `aria-current="page"`, 굵은 글씨, 왼쪽 강조선, 배경색으로 표시한다. 색상만으로 구분하지 않는다.
- 모바일에서는 햄버거 버튼으로 여는 서랍 메뉴로 바꾼다. 키보드 포커스가 서랍 안에 머물고, `Esc`와 화면 이동 시 닫힌다.
- 홈도 같은 공통 레이아웃을 사용하며, 홈에서는 어떤 주 메뉴도 선택 상태로 표시하지 않는다.

### 4.2 화면 안의 하위 메뉴

- 공통 `SectionNav` 컴포넌트를 만들고, 각 섹션 화면 본문 상단(페이지 제목 아래)에 **현재 섹션의 하위 메뉴만** 탭 형태 링크로 표시한다.
- 현재 하위 메뉴는 `aria-current="page"`와 밑줄·굵은 글씨로 표시한다.
- 모바일에서는 가로 스크롤로 처리한다.
- 하위 메뉴가 하나인 `나의 로드맵`도 같은 형태로 1개 탭을 표시해 일관성을 유지한다.

| 섹션 | 하위 메뉴 |
|---|---|
| 지원사업 찾기 | 기업정보 입력·저장 / 기업 진단 / 맞춤 추천 |
| 전체 지원사업 | 전체 공고 / 공고 달력 |
| 나의 로드맵 | 수출 로드맵 |
| 마이페이지 | 기업 프로필 / 관심·준비 중·신청완료 사업 / 서류함 (오른쪽 끝에 `로그아웃` 버튼) |

### 4.3 오른쪽 상단 헤더

| 인증 상태 | 표시 |
|---|---|
| 확인 중 | 프로필 자리만 비워 둔다. 가짜 아바타나 스켈레톤을 표시하지 않는다 |
| 비로그인 | `로그인` 버튼 → `/login?redirect=<현재 경로>` |
| 로그인 | 동그란 프로필(지름 36~40px, 계정 아이디 첫 글자, 예: `A`). 클릭 시 `/mypage/profile`로 바로 이동. 드롭다운 없음. `aria-label="마이페이지로 이동 (ADMIN 계정)"` 형식으로 실제 아이디를 넣는다. 마이페이지 안에서는 선택 상태로 표시 |

### 4.4 설명 문구 줄이기

- 각 페이지 상단은 제목 1개와 한 줄 설명까지만 둔다.
- 길게 반복되던 안내 문단은 삭제하지 말고, 해당 기능의 주 관리 화면 한 곳에 `자세히 보기` 펼침 영역으로 모은다. 다른 화면에는 한 줄 요약과 링크만 둔다.

## 5. 홈

### 5.1 본문 구성 (위에서 아래 순서)

1. **첫 화면**: 서비스 한 줄 소개만 크게 표시한다.
   `우리 회사에 맞는 수출지원사업을 찾아보세요.`
   첫 화면 높이는 `100svh - 헤더 높이` 정도로 잡고, 아래로 스크롤할 수 있다는 작은 표시를 둘 수 있다 (`aria-hidden` 처리).
2. **이용 방법 3단계** (스크롤 후)
   - ① 기업정보 입력 — 회사의 기본 정보와 수출 현황을 입력합니다.
   - ② 맞춤 지원사업 확인 — 신청자격과 추천 이유를 확인합니다.
   - ③ 비교 및 신청 준비 — 공고를 비교하고 필요한 서류를 준비합니다.

   각 단계는 제목과 한 줄 설명만 둔다. 클릭 가능한 카드로 만들지 않는다 (메뉴 중복 방지).
3. **`추천받기` 버튼**: 3단계 안내 바로 아래에 주요 버튼으로 둔다.

### 5.2 홈에서 제거할 요소

한눈에 보기 카드(접수 공고 건수·추천 건수 `-`), 판단 순서 설명, 전체 메뉴 안내, 반복되는 시작 안내, 기존 `기업정보 입력하기` CTA(→ `추천받기`로 대체).

제거 전에 확인한다.
- 데이터 준비 상태 안내가 전체 공고와 맞춤 추천의 빈 상태 문구에 있는지 확인하고, 없으면 그곳으로 옮긴다.
- 판단 순서(신청 자격 → 적합도 → 준비 부담) 설명은 맞춤 추천 하단의 `추천 기준 안내`로 옮긴다 (§8).

### 5.3 `추천받기` 이동 규칙

| 상태 | 동작 |
|---|---|
| 인증 확인 중 | 확인이 끝날 때까지 기다린 뒤 아래 규칙 적용 (버튼 `aria-busy`) |
| 로그인 | `/diagnose/input` (지원사업 찾기 > 기업정보 입력·저장) |
| 비로그인 | `/login?redirect=/diagnose/input` |

- 로그인 또는 회원가입이 끝나면 `redirect` 값으로 이동한다. 따라서 홈의 `추천받기`로 들어온 사용자는 완료 후 지원사업 찾기로 연결된다.
- `redirect`는 `/`로 시작하고 `//`나 `://`가 없으며 등록된 라우트와 일치할 때만 사용한다. 그 외에는 `/`로 이동한다 (외부 주소로의 이동 방지).
- `redirect` 없이 로그인한 경우 `/`로 이동한다.

## 6. 인증 (로그인·회원가입)

### 6.1 원칙

- **서버가 확인한 결과만 로그인 상태로 인정한다.** localStorage·sessionStorage에 "로그인됨" 같은 플래그를 저장해 로그인 상태를 판단하지 않는다.
- 비밀번호와 세션 비밀키는 프론트엔드 소스, 빌드 결과물, README, Git 커밋에 넣지 않는다.
- 서버 전용 환경변수에 `VITE_` 접두사를 붙이지 않는다. `VITE_` 변수는 브라우저 번들에 그대로 포함된다.
- 로그인 여부와 관계없이 기업정보와 관리 기록은 기존처럼 이 브라우저에 저장된다. `이 기기에서만 보관` 안내를 유지하고, 서버 동기화가 되는 것처럼 표현하지 않는다.

### 6.2 경우 A: 실제 서버 인증이 이미 있는 경우

- 기존 인증 API와 세션 방식을 재사용한다.
- 데모 계정은 Django 관리 명령(예: `python manage.py ensure_demo_user`)으로 만든다. 값은 환경변수 `DEMO_LOGIN_ID`, `DEMO_LOGIN_PASSWORD`에서 읽고, 여러 번 실행해도 계정이 중복 생성되지 않게 한다. `is_staff=False`, `is_superuser=False`.
- 프론트엔드와 백엔드 도메인이 다르면 Vercel rewrite로 `/api/*`를 백엔드로 프록시해 같은 출처로 맞추는 방식을 우선한다. 불가능하면 CORS(credentials 허용)·CSRF·쿠키(`SameSite=None; Secure`) 설정을 함께 맞춘다.

### 6.3 경우 B·C: 프론트엔드만 배포된 경우 (예상)

Django 서버를 이번에 새로 배포하지 않고, Vercel 서버 함수로 데모 계정의 로그인을 서버에서 검증한다.

**파일 구성 (예시)**

| 파일 | 역할 |
|---|---|
| `frontend/server/auth/core.ts` | 순수 함수: 자격 증명 확인, 세션 토큰 생성·검증, 쿠키 직렬화·파싱 |
| `frontend/api/auth/login.ts` | `POST` 로그인 |
| `frontend/api/auth/logout.ts` | `POST` 로그아웃 (쿠키 삭제) |
| `frontend/api/auth/me.ts` | `GET` 현재 로그인 상태 |
| `frontend/api/auth/signup.ts` | `POST` 회원가입 (경우 B에서는 `501` 응답) |
| `frontend/server/devAuthPlugin.ts` | Vite 개발 서버 미들웨어. 위 핸들러를 `configureServer`·`configurePreviewServer`에 연결해 `npm run dev`·`npm run preview`에서도 로그인이 동작하게 함 |

- Vercel 프로젝트의 Root Directory가 `frontend`이므로 서버 함수는 `frontend/api/`에 둔다.
- 함수 작성 전에 Vercel 공식 문서에서 현재 Node.js 런타임의 함수 시그니처(Web `Request`/`Response` 방식 등)를 확인하고 그에 맞춘다.
- 서버 코드(`api/`, `server/`)는 Node 타입을 쓰는 별도 tsconfig로 타입 검사하고, 브라우저 앱 번들에 포함되지 않게 한다.

**환경변수 (서버 전용)**

| 이름 | 내용 |
|---|---|
| `DEMO_LOGIN_ID` | 데모 아이디 |
| `DEMO_LOGIN_PASSWORD` | 데모 비밀번호 |
| `AUTH_SESSION_SECRET` | 세션 서명 키. `openssl rand -base64 32`로 생성. 로컬·Preview·Production 각각 다른 값 |

**동작 규칙**

- **로그인:** 요청 본문 `{ id, password }`. 아이디는 대소문자를 구분해 정확히 일치해야 한다. 비교는 두 값의 SHA-256 해시를 `crypto.timingSafeEqual`로 비교한다. 실패 시 `401`과 함께 `아이디 또는 비밀번호가 올바르지 않습니다.`라고만 안내한다 (어느 쪽이 틀렸는지 알려주지 않음).
- **세션:** `{ sub, iat, exp }`를 HMAC-SHA256으로 서명한 토큰을 쿠키 `esm_session`에 저장한다.
  - 쿠키 속성: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` 12시간, 배포 환경에서 `Secure`
  - 서명이나 만료가 맞지 않으면 비로그인으로 처리한다.
- **현재 상태:** `GET /api/auth/me`는 `200`과 함께 `{ authenticated: true, user: { id } }` 또는 `{ authenticated: false }`를 반환한다.
- **환경변수가 없을 때:** 로그인 API는 `503`과 `로그인 설정이 되어 있지 않습니다.`를 반환한다. 코드 안의 기본값 아이디·비밀번호로 대신하지 않는다.
- **회원가입 (경우 B):** 회원 정보를 저장할 서버 DB가 없으므로 실제 가입을 처리하지 않는다.
  - 로그인 화면에 `회원가입` 탭과 입력 항목(아이디, 비밀번호, 비밀번호 확인)은 표시한다.
  - 제출 버튼은 비활성화하고 이유를 보여준다: `회원 정보를 저장할 서버가 아직 연결되지 않아 회원가입은 준비 중입니다. 데모 계정으로 로그인해 확인할 수 있습니다.`
  - 브라우저 저장소에 가입 정보를 만들어 가입된 것처럼 꾸미지 않는다.
  - 나중에 실제 회원가입이 연결되면 로그인과 같은 `redirect` 규칙을 그대로 적용한다 (§5.3).

### 6.4 데모 계정

| 항목 | 값 |
|---|---|
| 아이디 | `ADMIN` |
| 비밀번호 | `********` |
| 권한 | 일반 사용자와 동일. 관리자 권한 없음. 로그인 후 화면 흐름 확인 전용 |

- 이 값은 `frontend/.env.local`(Git 제외)과 Vercel 프로젝트 환경변수(Production·Preview)에만 넣는다.
- `.env.example`에는 변수 이름만 적고 값은 비워 둔다.
- README에는 "데모 계정은 환경변수로 설정한다"는 설명과 변수 이름만 적는다.
- **이 문서 자체에도 비밀번호가 있다.** 루트의 `revision_01.md`는 `.gitignore`에 추가하고, 비밀번호를 `********`로 가린 사본을 `docs/revisions/revision_01.md`로 커밋한다.

### 6.5 프론트엔드 인증 상태

- 프로젝트의 기존 상태 관리 방식으로 `useAuth`(또는 auth store)를 만든다.
  - 상태: `status: 'unknown' | 'authenticated' | 'anonymous'`, `user: { id } | null`, `errorMessage`
- 앱 시작 시 `/api/auth/me`를 한 번 호출하고, `router.beforeEach`는 이 확인이 끝난 뒤 진행한다.
- 네트워크 오류로 확인할 수 없으면 비로그인으로 처리하고, 로그인 화면에 `로그인 상태를 확인할 수 없습니다. 잠시 후 다시 시도해 주세요.`를 표시한다.
- 로그인 성공 시 상태를 갱신하고 `redirect`로 이동한다. 로그아웃 시 서버 쿠키를 지우고 상태를 갱신한 뒤 `/`로 이동한다. 로그아웃해도 이 기기에 저장된 기업정보와 관리 기록은 지우지 않는다.

### 6.6 접근 제한

- `meta.requiresAuth`가 있는 화면(마이페이지 전체)에 비로그인 상태로 접근하면 `/login?redirect=<원래 전체 경로>`로 보낸다.
- 이미 로그인한 상태에서 `/login`에 접근하면 `redirect` 또는 `/`로 보낸다.
- 그 밖의 화면은 기존처럼 비로그인으로도 접근할 수 있다. 기업정보 입력·저장도 기존 동작을 유지한다.

## 8. 맞춤 추천 (`/programs/recommended`)

### 8.1 화면 순서

1. 페이지 제목과 한 줄 설명
2. 간단한 도구 줄: 결과 건수(`-`), 기존 필터·정렬. 모바일에서는 `필터` 버튼으로 접는다.
3. **추천 결과 목록 또는 빈 상태** — 반드시 큰 설명 영역보다 위에 둔다.
4. 하단 `추천 기준 안내` 펼침 영역 (기본 닫힘): 기존의 신청 자격·적합도·준비 부담 설명과 홈에서 옮겨 온 판단 순서 설명. 삭제하지 않고 이곳으로 옮긴다.

### 8.2 추천 카드 (`RecommendationCard`)

기본으로 보이는 정보는 네 가지다.

| 항목 | 값이 있을 때 | 값이 없을 때 |
|---|---|---|
| 공고명 | 공고명 (클릭 시 `/programs/:id?from=recommended`) | - |
| 신청자격 | `신청 가능` / `확인 필요` / `신청 불가` 배지. 아이콘과 글자를 함께 표시 | `신청자격 -` |
| 마감일 | `applyEnd`를 `YYYY.MM.DD`로 표시 | `마감일 -` |
| 추천 이유 | `reasons[0]`을 한 줄로 표시. 넘치면 말줄임, 전체 문장은 펼침 영역에 표시 | `추천 이유 -` |

- **`계산 근거 보기`** 펼침 버튼(`aria-expanded`, `aria-controls`)
  - 근거가 있을 때: 적합도, 항목명, 반영값, 가중치, 근거 문장, 원문 출처, 계산 기준일·버전
  - `FitScoreResult`가 `null`이거나 항목이 비어 있을 때: `아직 계산 근거가 없습니다. 공고 규칙과 적합도 기준이 연결되면 항목별 근거가 표시됩니다.` 숫자를 임의로 만들지 않는다.
- 기존 카드 동작은 삭제하지 않고 작게 유지한다.
  - `상세보기`: 공고명 링크로 대체
  - `비교에 추가`: §9.3의 공통 비교 선택에 추가
  - `관심사업 저장`: 마이페이지 관리 기록에 `관심` 상태로 추가. 비로그인이면 로그인 화면으로 보낸 뒤 이 화면으로 돌아온다
  - 공고가 없는 현재는 기존처럼 비활성 상태와 이유를 유지한다.
- `신청 불가` 카드는 다른 카드 뒤에 두고, 적합도보다 신청자격을 먼저 표시한다 (기존 원칙).
- 카드 안에 기관·지원규모·지원방식 등 다른 지표를 쌓지 않는다. 이런 정보는 상세 화면에서 확인한다.
- 기존 `비교 진입 안내` 큰 영역은 제거하고, `비교에 추가` 동작으로 대체한다.
- 화면에 가짜 카드를 렌더링하지 않는다. 컴포넌트 테스트가 필요하면 테스트 폴더 안의 테스트 전용 데이터만 쓰고, 앱 코드에서 이를 불러오지 않는다.

## 9. 전체 공고와 공고 비교 통합 (`/programs`)

### 9.1 화면 구성

1. 기존 검색·필터·정렬과 결과 목록
2. 결과의 각 공고에 `비교에 추가` 체크박스. 공고가 없을 때는 기존처럼 비활성 상태와 이유를 표시
3. **하단 `공고 비교` 영역** (`id="compare"`)

### 9.2 공고 비교 영역

- 머리말: `선택한 공고 n/4` (실제 선택 개수)
- 선택한 공고를 칩으로 표시한다 (공고명, 개별 제거 버튼, `모두 지우기`).
- **`비교 내용 펼치기`** 버튼(`aria-expanded`)을 누르면 기존 비교 표 컴포넌트를 표시한다. 새로 만들지 말고 기존 컴포넌트를 옮겨서 재사용한다.
  - 최대 4개 열
  - 기존 행 유지: 자격상태, 적합도, 기간, 지원규모·방식, 지원분야, 필요서류, 예상 준비 시간, 새로 준비할 문서, 자기부담금, 수행 후 의무, 중복수혜/유사사업, 원문
  - 기존의 중복·충돌·기회비용 영역 유지
  - 모바일 가로 스크롤/카드 보기 유지
  - 어떤 사업이 더 좋다고 판단하지 않는다
- 선택이 2개 미만일 때 펼치면 기존의 `-` 빈 비교 표와 함께 `비교하려면 공고를 2개 이상 선택하세요.`를 표시한다.
- 5번째 공고를 추가하려 하면 추가하지 않고 `최대 4개까지 비교할 수 있습니다.`를 안내한다.
- 선택이 1개 이상이면 전체 공고 화면 하단에 작은 고정 바(`비교 n/4 · 비교 영역으로 이동`)를 표시해 긴 목록에서도 비교 영역을 찾을 수 있게 한다.

### 9.3 비교 선택 상태 (모든 화면 공통)

- 공통 `useCompareSelection` 하나로 관리한다. 기존 비교 페이지가 쓰던 저장 방식·키가 있으면 그대로 재사용한다.
- 선택 상태는 URL 쿼리 `compare=id1,id2`(히스토리를 쌓지 않는 replace 방식)와 sessionStorage에 함께 반영한다. 순서 유지, 중복 제거, 최대 4개.
- 저장된 ID가 `ProgramRepository`에서 조회되지 않으면 조용히 버리지 않는다. `찾을 수 없는 공고`로 표시하고 제거 버튼을 제공한다.
- 다른 화면(맞춤 추천 카드, 공고 상세, §2 조사에서 찾은 기타 진입점)의 비교 버튼은 선택에 추가한 뒤 `/programs?compare=…#compare`로 이동한다. 도착하면 비교 영역으로 스크롤하고, 2개 이상이면 자동으로 펼친다.
- 기존 독립 비교 페이지는 메뉴에서 제거하고, 경로는 리다이렉트로만 남긴다 (§3.2).

## 10. 공고 달력 (`/programs/calendar`)

- 기존 `마이페이지 > 일정`의 화면과 컴포넌트를 **옮긴다** (새로 작성하지 않음).
- 기존 기능을 모두 유지한다: 월 이동, 오늘 이동, 일정 유형 구분(접수 시작, 마감, 발표, 협약, 개인 준비 목표), 범례·필터, 빈 상태, 목록 보기(있었다면).
- 공고 일정은 `ProgramRepository`의 실제 날짜 필드에서만 만든다.
  - `applyStart` → 접수 시작
  - `applyEnd` → 마감
  - 발표·협약일 필드가 `Program` 타입에 없으면 `resultAnnounceAt`, `agreementAt`를 `null` 기본값의 선택 필드로 추가한다.
  - 공고 날짜가 없으면 일정을 만들지 않는다. 가상 일정 금지.
- 개인 준비 목표가 기존에 브라우저에 저장되고 있었다면 같은 저장 키로 계속 표시한다.
- 일정을 누르면 `/programs/:id?from=calendar`로 이동한다.
- `오늘` 날짜는 달력 이동에만 쓰고, 공고 날짜처럼 사용하지 않는다 (기존 원칙).
- 마이페이지의 `일정` 메뉴·요약 카드를 제거하고, `/mypage/calendar`는 리다이렉트로 연결한다.

## 11. 마이페이지 (로그인 필요)

### 11.1 기업 프로필 (`/mypage/profile`)

- 저장된 기업정보를 **조회만** 한다. 기업정보 입력 페이지가 쓰는 저장소·store를 그대로 읽는다 (별도 사본 금지).
- 미입력은 `-`, 사용자가 입력한 `0`은 `0`으로 표시하고, `입력 중`/`입력 완료` 상태를 기존처럼 표시한다.
- `기업정보 수정` 버튼 → `/diagnose/input` (단계 지정은 §7.1 규칙).
- 마이페이지 안의 별도 수정 폼은 제거한다.
- **제거 전 확인:** 기존 마이페이지 수정 폼에서만 고칠 수 있던 항목이 있는지 기업정보 입력 페이지와 대조한다. 그런 항목이 있으면 입력 페이지를 고치지 말고, 해당 항목의 수정 기능은 남겨 둔 채 최종 보고에 적는다.
- `이 기기에서만 보관` 안내를 유지한다.

### 11.2 관심·준비 중·신청완료 사업 (`/mypage/programs`)

하나의 관리 화면 안에서 상태별 탭(`role="tablist"`, URL `?tab=`과 동기화)으로 나눈다.

**상태 값 (한 곳에서 정의)**

| 값 | 표시 | 의미 | 탭 |
|---|---|---|---|
| `interested` | 관심 | 저장만 한 사업 | 관심 |
| `preparing` | 준비 중 | 서류·계획서 준비 중 | 준비 중 |
| `applied` | 신청완료 | 신청서를 제출하고 결과를 기다리는 상태 | 신청완료 |
| `under_review` | 심사중 | | 신청완료 |
| `selected` | 선정완료 | 선정 통보를 받은 상태 | 신청완료 |
| `not_selected` | 미선정 | | 신청완료 |
| `in_progress` | 수행중 | | 신청완료 |
| `completed` | 완료 | | 신청완료 |

- `신청완료`와 `선정완료`는 서로 다른 상태 값과 배지 문구로 구분한다. 신청완료 탭에는 상태별 필터 칩(전체 / 신청완료 / 심사중 / 선정완료 / 미선정 / 수행중 / 완료)을 둔다.
- 기존 기능을 탭 안에 모두 옮긴다.
  - 관심 탭: 기존 관심 사업 목록 기능
  - 준비 중 탭: 준비도 `-`, 체크리스트·사업계획서 연결 자리
  - 신청완료 탭: 기존 지원 이력 기능 (상태 변경, 상태 이력, 메모)
- **날짜 규칙:** 상태를 바꾼 시각은 사용자의 실제 행동 시각이므로 시스템 시각으로 기록할 수 있다. 신청일·발표일 같은 업무 날짜는 사용자가 입력한 값만 저장한다.
- 기록이 없으면 탭마다 빈 상태 안내를 표시한다. 공고가 없을 때 새 기록 등록은 기존처럼 비활성 상태와 이유를 표시한다.

**데이터 보존·병합**

- §2에서 찾은 기존 관심·준비·이력 저장 키를 읽는 통합 store를 만든다. 이미 통합된 구조가 있으면 그대로 재사용한다.
- 새 키(예: `esm.applicationRecords.v1`)로 옮길 때는 한 번만 실행되는 마이그레이션으로 복사·병합하고, **기존 키는 지우지 않는다.**
- 같은 공고가 여러 목록에 있으면 가장 진행된 상태를 현재 상태로 두고, 모든 상태 이력과 메모를 보존한다.
- 마이그레이션 완료 표시를 저장해 중복 실행을 막는다.

### 11.3 서류함 (`/mypage/documents`)

기존 기능과 화면을 유지한다. 공통 레이아웃과 하위 메뉴만 적용한다.

### 11.4 기존 마이페이지 홈

`/mypage`는 `/mypage/profile`로 리다이렉트한다. 기존 홈의 요약 카드(저장한 사업, 준비 중 사업, 일정, 지원 이력, 서류, 로드맵)는 각 기능의 주 관리 화면으로 바로가기만 하던 중복 요소이므로 제거한다. 각 기능은 해당 주 관리 화면에서 그대로 쓸 수 있다.

## 12. 중복 기능 정리 기준

| 기능 | 주 관리 위치 | 다른 화면에서 허용되는 것 |
|---|---|---|
| 기업정보 입력·수정 | 지원사업 찾기 > 기업정보 입력·저장 | 요약 표시, `기업정보 수정` 바로가기 (기업 진단, 기업 프로필) |
| 공고 검색·비교 | 전체 지원사업 > 전체 공고 (하단 비교) | `비교에 추가` 버튼 → 선택 유지 후 비교 영역으로 이동 |
| 공고 일정 | 전체 지원사업 > 공고 달력 | 마감일 텍스트 표시, `달력에서 보기` 링크 |
| 관심·준비·신청 상태 관리 | 마이페이지 > 관심·준비 중·신청완료 사업 | `관심사업 저장` 버튼(기록 생성만), 현재 상태 배지 표시 |
| 단계별 성장 계획 | 나의 로드맵 > 수출 로드맵 | 기업 진단의 `로드맵 보기` 바로가기 |

- 같은 폼, 표, 달력, 상태 관리 목록을 두 곳 이상에 구현하지 않는다. 컴포넌트를 복사하지 말고 재사용하거나 링크로 바꾼다.
- 같은 설명 문단을 여러 화면에 반복하지 않는다 (§4.4).

## 13. 로컬·배포 반영 절차

### 13.1 로컬

1. `frontend/.env.local`에 `DEMO_LOGIN_ID`, `DEMO_LOGIN_PASSWORD`, `AUTH_SESSION_SECRET`을 설정한다 (Git 제외 확인).
2. `.env.example`에 변수 이름만 추가한다.
3. `npm install` → `npm run dev`에서 로그인·로그아웃·리다이렉트가 동작하는지 확인한다.
4. `npm run build` → `npm run preview`에서도 같은 동작을 확인한다.

### 13.2 Vercel

1. 기존 Vercel 프로젝트(`exportsupportmatching`)의 환경변수에 세 값을 Production·Preview로 추가한다. `AUTH_SESSION_SECRET`은 환경별로 다른 값을 쓴다.
2. 환경변수는 추가한 뒤 새로 배포해야 적용된다.
3. `frontend/vercel.json`의 SPA rewrite가 `/api/`를 가로채지 않게 한다.
   ```json
   { "rewrites": [{ "source": "/((?!api/).*)", "destination": "/index.html" }] }
   ```
   기존 설정(헤더 등)은 유지하고 rewrite만 조정한다.
4. Git 연동 배포라면 커밋·푸시 → Preview URL에서 §14 검증 → Production 반영. CLI 연동이라면 `vercel` → 검증 → `vercel --prod`.
5. Production 주소는 `https://exportsupportmatching.vercel.app/`를 유지한다.
6. GitHub·Vercel 접근 권한이 없어 배포하지 못하면 URL을 지어내지 말고, 필요한 연결·설정과 남은 명령을 정확히 보고한다 (기존 `CLAUDE.md` §9 원칙).

### 13.3 Git

- `frontend/.env.local`과 루트 `revision_01.md`가 커밋되지 않았는지 확인한다.
- 가린 사본 `docs/revisions/revision_01.md`와 `docs/revisions/revision_01_inventory.md`를 커밋한다.
- 커밋은 의미 단위로 나눈다 (예: 내비게이션, 인증, 비교 통합, 달력 이동, 마이페이지 통합).

## 부록. 이 문서가 정한 결정 사항

사용자 지시에 명시되지 않아 이 문서에서 정한 내용이다. 다르게 하고 싶으면 이 표를 고친 뒤 다시 요청한다.

| 번호 | 결정 | 이유 |
|---|---|---|
| 1 | 로그인이 필요한 화면은 마이페이지뿐이다 | 다른 화면을 막으면 기존에 되던 비로그인 이용이 사라진다 |
| 2 | 서버 DB가 없으면 회원가입은 `준비 중`으로 비활성화한다 | 가입 정보를 저장할 곳 없이 가입된 것처럼 보이면 안 된다 |
| 3 | `/mypage`는 기업 프로필로 리다이렉트하고 마이페이지 홈 요약 카드는 제거한다 | 각 카드가 다른 화면의 바로가기였던 중복 요소다 |
| 4 | 심사중~완료 상태는 신청완료 탭 안에서 배지와 필터로 구분한다 | 탭은 지시대로 3개를 유지하면서 기존 지원 이력 상태를 보존한다 |
| 5 | 이동하지 않는 화면은 기존 URL을 유지한다 | 기존 링크·북마크가 깨지지 않는다 |
| 6 | `관심사업 저장`은 로그인이 필요하다 | 저장한 기록을 관리하는 마이페이지가 로그인 화면이기 때문이다 |
| 7 | 공고 상세는 전체 지원사업 섹션에 속하고, `from` 값으로 돌아갈 화면을 정한다 | 추천·달력에서 들어와도 원래 화면으로 돌아갈 수 있다 |
| 8 | 데모 아이디는 대소문자를 구분한다 | 서버 검증 규칙을 단순하고 명확하게 유지한다 |
